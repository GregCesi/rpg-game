# Xéros

Jeu d'aventure en pixel art, vue de dessus. On suit Xéros, jeune paysan d'un petit village, qui découvre le monde au fil de ses péripéties. Ton médiéval fantastique, terre à terre.

Phaser 3 + TypeScript + Vite. Tuiles 32×32.

## Lancer

```bash
npm install
npm run dev            # http://localhost:5173  (?debug : collisions ; ?reset : efface la sauvegarde ; ?dieu : outils de test)
npm run art            # art/ -> PNG, manifestes et tilesets Tiled (à lancer une fois avant d'ouvrir Tiled)
npm run maps           # cartes Tiled (tiled/maps/*.tmj) -> src/generated/maps.ts
npm run sketch -- <id> # fait naître tiled/maps/<id>.tmj depuis tiled/sketches/<id>.json (grille de lettres)
npm run test           # test de non-régression de l'outil d'esquisse
npm run check          # art, maps, puis vérifie tout le contenu sans lancer le jeu (formats + références croisées)
npm run build          # check, test, puis build web dans dist/
npm run build:single   # un seul fichier HTML autonome dans dist-single/
npx tsx tools/preview-module.ts <module d'art> <dossier>  # aperçu x4 d'un seul module de dessin, sans importer tout art/ (quand plusieurs dessinateurs travaillent ensemble)
npm run art:preview    # régénère les sprites + aperçus x4 dans .art-preview/ (planche collection.png, xeros-<geste>-<outil>.png pour chaque geste et chaque outil en main, les deux mains hands.png, les tas piles.png : chaque genre étape par étape, collisions en liseré, et pour un genre lié, le lien seul puis la construction type posée dessus ; les trois arbres à chaque étape arbres.png (debout, chute à droite et à gauche, couché tel que le jeu le pose, entaille, billes, tas : le gros grand, le têtard, puis le normal, l'un sous l'autre ; un avertissement `ATTENTION arbres` si la dernière image d'une chute n'est pas, pixel pour pixel, l'arbre couché posé), les étalons du gabarit gabarit.png : Xéros, cube de 50 cm, bille est-ouest, bille nord-sud, cylindre debout de 50 cm, et la taille attendue en liseré ; chaque bâtiment de buildings.json qui monte, étape par étape, à sa place sur sa carte : woodshed-1.png à woodshed-5.png, woodshed-6.png Xéros dessous et le toit effacé, woodshed.png les met côte à côte)
```

Adresses de test (à combiner : `?dieu&debug`) : `?debug` montre les collisions ; `?reset` efface la sauvegarde et repart du réveil dans le cagibi (le mot est ensuite retiré de l'adresse : un rechargement reprend la nouvelle partie) ; `?dieu` ouvre à droite du jeu un panneau d'outils de test, à la souris (donner un objet en main, poser un objet du monde ou un tas devant Xéros, avec une longueur pour le rouleau de corde et un lien pour le tas de branches, aller sur une carte, remettre la carte ou la partie à zéro). Sans `?dieu`, le panneau n'existe pas.

Les cartes se font dans [Tiled](https://www.mapeditor.org/) : ouvrir `tiled/xeros.tiled-project`. Après une modification d'une carte, relancer `npm run dev` (ou `npm run maps`) pour la voir en jeu.

Commandes (touches lues par leur place sur le clavier, `KeyboardEvent.code` : même place en AZERTY et en QWERTY) : ZQSD (WASD en QWERTY) ou flèches. Maj pour courir. E (ou Entrée) : prendre dans une main libre (ramasser, prendre une bille, reprendre d'un tas, cueillir), parler, poser ce que tient la main active sur ce qui l'accepte (le rouleau sur le billot), ou reposer devant soi ce qu'on tient à deux mains. E maintenu une demi-seconde, mains libres, devant un tas de branches ou un fagot : nouer, dénouer (une jauge se remplit au-dessus de Xéros ; relâché avant, c'est E court). Q d'un clavier QWERTY, soit **A en AZERTY** (pour ne pas croiser le Q de ZQSD) : lâcher devant soi ce que tient la main active. Tab : changer de main active. R : tourner la bille portée (est-ouest, nord-sud). Espace : utiliser ce qu'on tient. E, Espace ou Entrée font défiler un dialogue.

## Architecture

  ui/                cadre de dialogue, flèche, touche E, cases des deux mains

tiled/               les cartes, faites avec Tiled
  xeros.tiled-project  projet Tiled (généré par build-art, committé) : types d'objets de props.json, Spawn, Exit
  maps/              les cartes (.tmj), éditées dans Tiled

tools/lib/           registre de tuiles, fichiers Tiled générés, schémas Zod du format Tiled, conversion des esquisses
tools/test-sketch.ts npm run test ; ses fixtures (anciennes cartes à lettres + .tmj figés) sont dans tools/fixtures/sketch/
tools/check.ts       npm run check : vérifie le contenu contre ce que art/ a produit
src/

  events.ts          noms des événements échangés entre scènes
  content/           le contenu du jeu, en JSON : tuiles (propriétés), objets, personnages, dialogues
    types.ts         formats du contenu (schémas Zod = types TypeScript + vérification), dont le format interne des cartes
    validate.ts      vérifications croisées (une sortie vers une carte qui existe, une image dessinée...)
    items.json       objets possédables (dans les mains, au sol)
    piles.json       genres de tas : ce qu'on y entrepose, ses places (couche, porteuses, pièce dessinée, collision)
    buildings.json   bâtiments : leurs pièces (objets de props.json), étape par étape dans l'ordre du chantier, et la carte où ils sont posés

  entities/Strength.ts composant : la force (porter, marcher chargé, rouler), seuils de strength.json × le multiplicateur de ?dieu
  entities/Hold.ts   composant : ce qu'il tient se voit sur lui (posture du corps, objet posé au point d'accroche image par image)

### Comment tourne une image du monde

`WorldScene` assemble la carte, le joueur et les systèmes, puis arbitre selon son **mode** (`play`, `use`, `dialogue`, `transition`) : un seul à la fois. Chaque système fait une chose et rend son résultat à la scène (`InteractionSystem` dit quel objet a été utilisé, `findExit` dit quelle sortie est prise) ; c'est la scène qui décide quoi en faire. Une nouvelle mécanique = un fichier dans `systems/` + quelques lignes dans `WorldScene.update`.

Entre scènes, on passe par le bus du jeu avec les noms de `events.ts` (ex. `GameEvent.DialogueEnd`, `GameEvent.HandsChanged`, `GameEvent.Notice`). À l'intérieur d'une scène, pas d'événements : des appels directs, plus faciles à suivre.

### L'état de la partie

Les cartes décrivent le monde au début de la partie ; `GameState` (`src/state/`, schéma Zod, indépendant de Phaser) dit ce qui a changé : les **deux mains** (`hands` : gauche et droite, chacune un objet ou rien ; `both` : ce qu'on tient à deux mains ; `active` : la main qui utilise et qui lâche ; un objet tenu est un objet possédable `{ item }` ou un objet du monde pris sur la carte `{ prop, flip }`, la bille), les objets de carte changés, rangés par carte et par **identifiant d'objet Tiled** (« objet 12 de la ferme : devenu `big-tree-stump` »), les objets posés au sol, par carte, et les **objets nés** pendant la partie (les pièces d'un arbre couché), par carte, avec leur identifiant propre, et les **tas** (`piles` : genre, point au sol, places prises, sens, lien), par carte ; un objet changé ou né peut être retourné (`flip`, ce qui est tombé vers la gauche) et porter une **longueur** (`length`, en cm : le rouleau de corde, ou le billot qui le porte), que garde aussi ce qu'on tient. La construction d'une carte (`GameMap`) applique ses changements et repose les objets nés. On le modifie par les fonctions de `state/GameState.ts` (`take`, `release`, `switchHand`, `changeObject`, `dropItem`, `spawnObject`, `changeSpawned`, `startPile`, `fillPlace`, `emptyPlace`, `addPile`, `removePile`, `setPileTie`, `turnHeld`, `emptyHands`, `resetMap`, `replaceState`...), jamais à la main depuis une scène : chacune avance un compteur de changements (`revisionOf`), et c'est lui qui déclenche la sauvegarde.

### La sauvegarde

La partie se sauvegarde toute seule, dans le navigateur (`localStorage['xeros-partie']`, `state/save.ts`) : `{ version, savedAt, where, state }`, `where` étant la carte, les pieds et la direction de Xéros, `state` le `GameState` tel quel. `systems/autosave.ts`, appelé au début de chaque `WorldScene.update`, l'écrit dès que le compteur a bougé (objet pris, posé, coupé, tas modifié...) ; la scène l'écrit aussi à l'arrivée sur une carte et quand la page se cache ou se ferme (`pagehide`, rechargement compris), pour garder la dernière position. Une position dans une zone de sortie (`exitAt`, `systems/exits.ts`) ne s'enregistre pas telle quelle : c'est le point d'arrivée de cette sortie, sur sa carte, qui est noté, pour que Xéros ne change pas de carte tout seul au rechargement. Au lancement, `BootScene` appelle `resumeGame` (`state/index.ts`) : la partie reprend à la position exacte (`at` de `WorldStart`), sinon au réveil (`START`). La lecture (`readSave`) ne plante jamais : sauvegarde illisible, d'une autre version (`SAVE_VERSION`), refusée par `SaveSchema`, ou qui nomme une carte, un objet ou une place de tas disparus du contenu : elle est mise de côté dans `localStorage['xeros-partie-abimee']` (détail en console), le HUD le dit en clair et la partie est neuve. **Changer le format de `GameState` d'une façon que l'ancien ne lit plus = augmenter `SAVE_VERSION`** (les anciennes sauvegardes sont alors refusées proprement). `?reset` passe par `clearSave`. La future sauvegarde au cagibi utilisera les mêmes fonctions.

### Les outils de test (`?dieu`)

`main.ts` ne charge `dieu/panel.ts` qu'avec `?dieu` et le monte à droite du canevas (`#stage` de `index.html`). Le panneau ne touche pas la partie : chaque bouton envoie une `DieuCommand` (`events.ts`) sur `GameEvent.Dieu`, que `WorldScene.dieu` exécute par les fonctions de `GameState`, donc tout est sauvegardé comme en jeu (refusé hors du mode `play`). Donner en main vide d'abord les mains (ce qu'elles tenaient disparaît) ; un objet qui a une longueur (le rouleau de corde, ou le billot qui le porte) se donne ou se pose avec la longueur choisie, en mètres ; un tas d'un genre lié (les branches) se pose « avec lien », de 0 pièce (le lien seul) au tas plein ; poser un objet du monde ou un tas passe par `HandsSystem.placeInFront` et `pileInFront` (même place libre que pour poser à la main ; le tas met toute son emprise au sol devant Xéros, places prises du bas vers le haut) ; aller sur une carte mène à son premier point d'apparition ; remettre la carte à zéro (`resetMap`) recharge la carte autour de Xéros ; réinitialiser la partie (« Toute la partie », à confirmer : le premier clic change le bouton en « Vraiment ? », le second agit ; sans second clic, il revient au bout de 3 s) efface la sauvegarde et repart du réveil. Les listes du panneau se lisent dans `props.json`, `items.json` et `piles.json` : le têtard (`big-pollard`), l'arbre normal (`normal-tree`), son tronc couché (sections, houppier, tête), ses billes (à porter) et son genre de tas (`normal-logs`) y sont d'office, comme ceux du gros, sans code de plus. Nouvel outil de test = une variante de `DieuCommand`, un bouton dans le panneau, un cas dans `WorldScene.dieu`.

### Les quatre règles

1. **Le contenu est de la donnée.** Une carte (un fichier Tiled), une tuile, un objet, plus tard une quête ou un dialogue : un fichier de données, pas une classe. Le moteur reste petit.
2. **Le pixel art est du texte.** Chaque sprite est une grille de caractères dans `art/`, convertie en PNG au build. On peut remplacer un PNG par un dessin fait à la main sans toucher au jeu : le jeu ne connaît que les clés (`xeros`, `world`, `big-tree`...).
3. **Composer plutôt qu'hériter.** Un personnage = un `Actor` (le corps) + un contrôleur (clavier, IA de PNJ). Les capacités (geste d'outil `ToolUse`, objets tenus `Hold`, plus tard stats, dialogue) sont des composants attachés, pas des sous-classes.
4. **Erreurs lisibles.** Une carte mal saisie ou un sprite de mauvaise taille doit planter avec un message qui dit où (la carte, l'objet, sa position). Les formats sont décrits une fois dans `content/types.ts` (Zod) ; la partie du format Tiled que l'on lit est décrite dans `tools/lib/tiled-schema.ts` et contrôlée par `build-maps` ; les liens entre fichiers sont vérifiés dans `content/validate.ts`, par `npm run check` et au démarrage du jeu (la liste des problèmes s'affiche à l'écran). Nouveau champ ou nouveau lien = on l'ajoute là.

### Conventions

- Animations : `<skin>-<état>-<direction>`, ex. `xeros-walk-left`. Directions : `down`, `up`, `left`, `right`.
- Ordre d'affichage : profondeur = position y des pieds (le joueur passe derrière un arbre). Les profondeurs fixes (sol, pénombre, lueurs, invite) sont dans `DEPTH` (`config.ts`).
- Collisions : toujours au niveau des pieds, jamais sur le sprite entier.
- Cartes : un fichier Tiled `tiled/maps/<id>.tmj` (l'id est le nom du fichier). Un calque de tuiles `ground` (le sol, toutes les cases peintes) et des calques d'objets au nom libre : c'est le **type** de chaque objet qui dit ce que c'est (`Spawn`, `Exit`, ou un objet de `props.json`). Propriétés de la carte : `name` (nom affiché) et `ambient` (pénombre des intérieurs, de 0 à 1). Le jeu de tuiles (`world` ou `interior`) se déduit du `.tsj` que la carte référence : un seul par carte, plus le tileset `props` pour poser les objets. Tuiles retournées, pivotées, intégrées ou redimensionnées : refusées avec un message.
- Nouvelle carte : on **esquisse**, puis on retouche dans Tiled. `tiled/sketches/<id>.json` décrit la carte en lettres (sol et objets, une lettre par case, `spawns` et `exits` en cases : l'ancien format de carte) ; la légende des lettres (lettre de sol -> tuiles ou terrain à raccord automatique, lettre d'objet -> clé de `props.json` et ancrage `center` ou `left`) est dans `tiled/sketch-legend.json`. `npm run sketch -- <id>` écrit `tiled/maps/<id>.tmj` (raccords automatiques, variantes au hasard stables, objets ancrés), puis on ouvre le résultat dans Tiled (`open -a Tiled tiled/xeros.tiled-project tiled/maps/<id>.tmj`). L'outil refuse d'écrire si le `.tmj` existe : l'esquisse ne sert qu'à la naissance, ensuite c'est le `.tmj` qui fait foi (les esquisses ne sont pas committées). Une lettre inconnue donne un message avec la lettre et sa position. `npm run test`, lancé par `npm run build`, repasse les anciennes cartes ferme et maison (fixtures) dans l'outil et exige les mêmes calques, objets, points et sorties que des copies figées de leurs `.tmj`.
- Le sol est peint avec son rendu final (pinceau terrain de Tiled) : le jeu affiche les tuiles telles quelles. Seuls les détails au hasard (touffes, paille…, `decals` de `tiles.json`) sont posés en jeu, de façon stable.
- Objets : type = clé de `props.json` (identifiant anglais en kebab-case : `big-tree`, `woodpile` ; son champ `name` est le nom affiché, en français), position au pixel (coin bas gauche de l'image : c'est aussi la profondeur d'affichage). Champ `interact` facultatif pour changer le dialogue de cet exemplaire.
- Points d'apparition : un point de type `Spawn`, son **nom** est son identifiant, `facing` facultatif. Position = les pieds du joueur.
- Personnages non joueurs : un point de type `Npc` (position = ses pieds), propriétés `character` (clé de `characters.json`, qui est aussi la clé de son sprite : il lui faut les animations `idle-down/up/left/right`), `dialogue` (clé de `dialogues.json`) et `facing` facultatif (`down` par défaut). Il est immobile, bloque le passage par ses pieds, se tourne vers Xéros pendant le dialogue puis reprend sa direction. `build-maps` le traduit en `npcs` de la carte ; `validate.ts` vérifie le personnage, le dialogue et les animations (message : carte, personnage, position). Pas encore de déplacement ni de journée type : un contrôleur d'IA viendra se brancher sur le même `Actor`.
- Sorties : un rectangle de type `Exit` (`to` = carte, `spawn` = point d'arrivée, `facing` facultatif). On la prend quand les pieds sont dedans, en avançant dans la direction `facing` si elle est donnée. C'est le premier type de zone ; d'autres suivront.
- Les tilesets de `tiled/tilesets/` et le fichier projet sont **générés** par `build-art` : on ne les modifie jamais dans Tiled (ils seraient réécrits). Pour changer une tuile ou un objet : `art/`, `tiles.json` ou `props.json`, puis `npm run art`.
- Numéros de tuiles : `art/tile-registry.json` (committé) donne à chaque tuile sa place, et les `.tmj` stockent ces numéros. Une tuile nouvelle est ajoutée en fin de liste par `npm run art` (committer le fichier) ; une tuile retirée de `art/` laisse un trou et ne peut plus être posée ; ne jamais réordonner. Renommer une tuile = changer son nom dans le registre **et** dans `art/`, à la même position.
- Départ de la partie : `START` dans `config.ts` (une partie sauvegardée reprend là où elle était, voir *La sauvegarde*).
- Raccords automatiques : clôtures, chemins, eau et cloisons (intérieur) sont des **terrains** (`terrains` de `tiles.json`) : une famille de 16 tuiles `<terrain>-<masque>` (masque N=1 E=2 S=4 O=8, un bit à 1 = le voisin est du même terrain). Dans le tileset de Tiled, chacun devient un ensemble Wang de type bord à deux couleurs : le terrain et « autre ». Une arête à 0 voudrait dire « indifférente » pour Tiled : elle n'est jamais utilisée, une arête absente du masque prend la couleur « autre », et les 16 `wangid` sont tous différents (vérifié par `build-art`). Limites connues : la cloison ne se raccorde pas d'elle-même aux murs, on pose la tuile d'accroche à la main ; en bord de carte, c'est le pinceau de Tiled qui choisit la tuile (une arête sans voisin), alors que l'ancien code comptait « hors de la carte » comme du même terrain : vérifier à l'œil les chemins qui sortent de l'écran.
- Objets (`props.json`) : `dims` (obligatoire) donne ses dimensions réelles en centimètres (`w` largeur, `d` profondeur, `h` hauteur, `shape` : `box`, `cylinder` avec `axis` `ew`/`ns`/`up`, ou `flat`) ; `validate.ts` en tire la taille attendue de sa silhouette d'après le gabarit (`src/content/gabarit.ts`, docs/STYLE.md section 8 : 5 cm par pixel, dessus et faces en raccourci à ½) et refuse un écart de plus de 2 px, sauf pour les objets anciens de `EXCEPTIONS` (`validate.ts`). La silhouette (pixels opaques, contour compris, ombre exclue) est calculée par `build-art` et notée dans le manifeste. `bodies` pour des collisions de forme libre, `anim` pour un objet animé (feu), `smoke` et `light` pour la fumée et les lueurs. Les collisions restent ici, pas dans Tiled.
- Tuiles (`tiles.json`) : `solid` (bloque le passage), `decals` (nom d'un ensemble de détails au hasard) et `terrains`. Les propriétés `solid` et `decals` apparaissent aussi comme propriétés de tuile dans le tileset de Tiled.
- Interactions : un objet de `props.json` avec `"interact": "<id>"` lance le dialogue `<id>` de `dialogues.json`.
- Objets possédables (`items.json`) : clé en anglais kebab-case, `name` en français, `icon` (`item-<clé>`, 16×16, dans les cases des mains), `ground` facultatif (son image couchée au sol, à l'échelle ; sinon l'icône : la branche a `branch-ground`, le même dessin que dans le tas et en main, `art/items/branch.ts`), `kind` (`tool`, `weapon`, `resource`), `hands` (1 par défaut, 2 pour ce qui est lourd ou long : la hache). Une main tient un seul objet ; pas de besace. Un objet au sol se prend avec E dans une main libre (les deux s'il le demande) ; sinon « Les mains pleines. ».
- Les deux mains : E prend dans une main libre (la main active si elle est libre), ou, quand les deux mains tiennent un seul objet, le repose devant soi (E ne vise alors que les personnages à qui parler) ; Q (A en AZERTY) lâche devant soi ce que tient la main active ; Tab change de main active ; Espace utilise ce qu'on tient (la hache à deux mains s'utilise). On ne pose qu'à une place libre devant soi (dans la carte, hors cases bloquantes, collisions d'objets et personnages ; sinon « Pas la place ici. »). Un objet possédable posé reste au sol (GameState, `ground`). Le tout : `systems/hands.ts` ; à l'écran, deux cases G et D, la main active marquée ; une main vide montre une main ouverte (`ui-hand-left`, `ui-hand-right`) ; ce qu'on tient à deux mains s'affiche dans la case droite, la gauche montrant `ui-hands-both`.
- Objets du monde à prendre : un objet de `props.json` avec un composant `take` (`hands` : 1 ou 2 ; `icon` : son icône dans les cases des mains, `item-big-felled-log` pour toutes les billes ; `hold` : comment il se voit tenu). Ni `harvest` ni `interact` avec (validate.ts). Pris avec E, il quitte la carte (GameState : objet né retiré, objet de Tiled noté disparu) ; posé, il revient comme objet né, à sa nouvelle place, et s'y retrouve après un changement de carte (sauf s'il s'entrepose, `pile` : il va alors en tas, voir Tas). Les billes de l'arbre normal se prennent à deux mains et se portent devant lui ; celles du gros arbre (203 kg) sont trop lourdes pour les 70 kg de Xéros : elles se roulent.
- Tas (`piles.json`, un genre par entrée, clé anglaise en kebab-case) : on construit un tas pièce par pièce. Un objet s'entrepose s'il a `pile` (dans `items.json`, ou dans le `take` de `props.json`) : la branche (`branches` : 10 places en triangle, 4 au sol, puis 3, 2, 1, tête-bêche), toutes les billes (`big-logs` : 3 au sol côte à côte, 2 dans les creux, 1 au sommet). Un genre : `piece` (ce qu'on en reprend, `item` ou `prop`, toujours l'ordinaire : une bille de tronc `big-felled-log-1..4` y devient `big-felled-log`), `start` (place de la première pièce d'un nouveau tas, au sol), `blockFrom` (nombre de pièces à partir duquel il bloque le passage : 3 pour les branches, 1 pour les billes) et `places`. Une place : `layer` (0 au sol), `on` (les places qui la portent : elle n'existe que quand elles sont prises), `image` (sa pièce : pour les branches, dessinée pour cette place dans `art/world/piles.ts`, `pile-branch-<place>` ; pour les billes, la bille ordinaire `big-felled-log` à toutes les places, qui ne change donc pas d'aspect d'une place à l'autre), `x`, `y` (coin bas gauche de l'image affichée, dans le repère du tas, point (0, 0) au sol), `body` (collision au sol, couche 0 seulement) et `aim` facultatif (point visé ; sinon le centre de `body`, au-dessus le milieu des porteuses). Une place au sol ne s'ouvre qu'en touchant une pièce déjà posée au sol. L'ordre d'affichage est `order` du genre (`drawOrder`, `src/world/pileShape.ts`) : `layers` (par défaut, les branches) couche par couche, du bas vers le haut, dans une couche de l'arrière vers l'avant ; `depth` (les billes) de l'arrière vers l'avant d'après le point visé au sol, à égalité la couche du bas d'abord, pour que la bille de devant cache un peu celle de derrière et le bas de celle qui repose dans le creux. Tout le tas est à la profondeur du bas de sa pièce la plus en avant ; les positions sont choisies pour qu'une pièce du dessus repose sur ses porteuses sans flotter. Poser (Q, ou E à deux mains) : à la place disponible d'un tas du même genre dont le point visé est le plus près du point que regarde Xéros (à portée d'`INTERACT.radius`), donc dans le creux quand il est au centre entre deux pièces, au sol à côté quand il est décalé ; une place au sol doit être libre (carte, objets, personnages, Xéros, pièces d'autres tas) ; sinon à la première place d'un nouveau tas, juste devant lui ; sinon « Pas la place ici. ». Une prévisualisation en transparence montre la pièce à la place exacte où elle ira, et suit Xéros. E, mains libres, vise les pièces les plus hautes qu'on peut enlever (rien ne repose dessus) et en reprend une ; le tas disparaît à la dernière. Les genres ne se mélangent pas. Un tas est un seul objet du monde (GameState, `piles` de la carte : genre, point au sol, places prises) ; chaque pièce au sol a sa collision. Le tout : `systems/hands.ts` (viser, prévisualiser, poser, reprendre), `GameMap.placePile` (affichage, collisions), `world/pileShape.ts` (places ouvertes, pièces à reprendre, ordre d'affichage, sans Phaser) ; `validate.ts` vérifie la pièce reprise, la place de départ, les images, les collisions au sol et les porteuses (couche juste en dessous). Aperçu : `npm run art:preview`, `.art-preview/piles.png` (construction type, puis tous les états possibles). Les branches lâchées par une récolte restent des objets au sol, éparpillées. Tas tourné : un genre peut avoir `turned` (`start`, `order`, `places` : sa forme nord-sud ; les billes, `big-felled-log-ns`, vue par le bout, 3 au sol d'ouest en est, 2 dans les creux, 1 au sommet, construit face à lui, Xéros au sud se déplaçant d'est en ouest) ; `shapeOf(def, turned)` (`pileShape.ts`) donne la forme d'un tas dans son sens. R tourne la bille portée (`turned` de ce qu'on tient dans GameState, `turnHeld`) si son genre a une forme tournée ; le fantôme suit. Un nouveau tas prend le sens de ce qu'on tient (`turned` du tas dans GameState) ; sur un tas posé, la pièce prend le sens du tas, quel que soit celui de ce qu'on tient ; une bille reprise d'un tas nord-sud reste tournée. La bille portée se voit de la même façon dans les deux sens.
- Corde, lien et fagot (fiches : `docs/objets/rope-coil.md`, `rope-tie.md`, `faggot.md`). **Quantité mesurée** : un objet de `props.json` avec `length` (`start`, longueur neuve en cm ; `cut`, ce qu'enlève une coupe ; `piece`, l'objet possédable qui tombe à chaque coupe) garde sa longueur restante dans GameState (`length` de ce qu'on tient, de l'objet né ou changé). Le rouleau de corde (`rope-coil`, 10 m, une main) est posé dans la réserve de `maison.tmj` ; il ne se range pas en tas ; tenu, sa longueur restante s'écrit en petit en bas de sa case de main (HudScene, signes `ui-digit-<chiffre>`, `ui-digit-comma`, `ui-digit-m`). **Poser sur** : `rest` d'un objet (`{ "<objet tenu>": "<ce qu'il devient>" }`) : E, l'objet tenu dans la main active, face à lui ; ce qu'il devient a `bears` (`prop`, l'objet porté, `empty`, ce qu'il redevient) : E, mains libres, reprend l'objet porté avec sa longueur, et son `harvest` (outil, geste) le coupe : chaque coup enlève `cut`, lâche `piece` au sol, et, vide, l'objet porté disparaît (`HarvestSystem.cutBorne`, message « Rouleau de corde : 8 m restants. »). Le billot : `chopping-block` + rouleau = `chopping-block-rope`, la hache coupe un lien (`rope-tie`, 2 m). **Lien d'un tas** : `tie` d'un genre de `piles.json` (`item`, l'objet possédable qui lie ; `north` et `south`, ses deux bouts courts qui dépassent sous le tas, chacun `image`, `x` et `dy` : le bout nord accroché au bord nord de la pièce au sol la plus au nord, le sud au bord sud de la plus au sud, pour qu'ils suivent la taille du tas, `tieImages` de `world/pileShape.ts` ; `alone`, son dessin seul par terre, une boucle lâche, coin bas gauche dans le repère du tas ; `into`, ce que devient le tas plein et lié une fois noué). Q d'un lien : sous le tas de ce genre sans lien le plus proche, à portée (il le ceinture par-dessous), sinon par terre devant Xéros, où il commence un tas sans pièce (GameState : `tie` du tas, `places` vide) ; le fantôme le montre. Le lien se dessine sous toutes les pièces. E sur un tas lié sans pièce reprend le lien. **Nouer, dénouer** (`systems/knot.ts`, E maintenu, mains libres) : un tas plein et lié devient un tas d'une pièce de `into` (le fagot), centré à sa place ; un fagot seul (tas d'une pièce, ou posé hors d'un tas) redevient le tas plein lié de son genre ; sinon « Il faut un lien. », « Pas assez de branches. », « Un seul fagot à la fois. », « Pas la place ici. ». **E maintenu** (`systems/longPress.ts`, `LONG_PRESS` de config.ts) : devant une cible que `KnotSystem.holds` reconnaît, l'appui attend ; relâché avant 500 ms, c'est E court (reprendre une pièce, le fagot), tenu jusqu'au bout, le geste long ; la jauge `ui-gauge` (animation `fill`) se remplit au-dessus de la tête ; Xéros qui vise autre chose abandonne l'appui. **Fagot** (`faggot`, 130 × Ø 50 cm, deux mains, `carry`) : genre `faggots`, même forme que les billes (6), tourné nord-sud (`faggot-ns`) avec R. **Nombre de pièces** : `count` d'un genre (les branches) : en tout petits chiffres (`ui-digit-<n>`) en bas à droite du tas, quand les pieds de Xéros sont à moins de `PILE_COUNT.near` px de ses pièces au sol (`systems/pileCount.ts`). `validate.ts` vérifie la pièce coupée, `rest` et `bears` réciproques, le lien (objet à une main, image, genre non tourné, `into` qui s'entrepose ailleurs), la jauge et les chiffres.
- Objets tenus, visibles sur Xéros à l'attente et à la marche (composant `Hold`) : `hold` d'un objet de `items.json` ou du `take` d'un objet de `props.json` = `stance` (posture : `hand`, bras pendants, un objet par main ; `shoulder`, la hache sur l'épaule, animations `shoulder-idle/walk-*` ; `carry`, porté devant lui à deux mains, `carry-idle/walk-*`) et `image`, la planche `held-<…>` (`art/items/carried.ts` : animations `down`, `up`, `right` d'une image, point d'accroche au centre ; la bille vue par le bout de profil). Sans `hold` : l'icône dans la main (à deux mains : `carry`). `hold.json` donne, par posture, état et direction, le point d'accroche de chaque image du corps (`dx`, `dy` depuis les pieds, `behind`) ; en posture `hand`, un point par main de Xéros (`left`, `right`, tirés de `HAND_POINTS` dans `art/characters/xeros.ts`, comme `SHOULDER_POINTS` et `CARRY_HANDS`). Vers la gauche : le miroir de la droite, mains échangées (la main côté spectateur n'est plus la même). Caché pendant un geste, où l'outil du geste prend sa place. Portant à deux mains (`carry`), il marche lentement (`PLAYER.carrySpeed`), ne court pas et n'utilise rien ; la hache sur l'épaule s'utilise. `validate.ts` vérifie les animations de chaque posture, leurs nombres d'images, les trois vues des planches et que la posture va avec les mains (`hand` pour une main).
- Masses et force (CONCEPTION, *Poids et force*). Tout objet qu'on prend, pose ou roule a une masse (`mass` dans `items.json` : un nombre ; dans `props.json` : un nombre, `"wood"` pour une pièce de bois cylindrique, calculée par ses `dims` × 900 kg/m³ après retrait du contour d'un pixel de chaque côté, ou `{ "pile": genre }` pour la somme d'un tas plein et de son lien) ; `validate.ts` refuse un objet qui se prend ou roule sans masse. `src/content/mass.ts` pèse (`propMass`, `itemMass`, `heldMass`). La force de Xéros est dans `strength.json` (`carry` 70, `walk` 25, `roll` 300 kg, `slowest` 0,5) et le composant `entities/Strength.ts` (`load` = masse portée, mise à jour par `WorldScene.handsChanged`) ; E refuse ce qui dépasse `carry` (`systems/weight.ts`). Porté au-delà de `walk` : pas de course, marche ralentie jusqu'à `slowest` à `carry` (`Player.update`). Une sauvegarde qui tient trop lourd pose l'objet au sol au chargement (`WorldScene.dropHeavy`). Les billes du gros arbre (203 kg) ne se portent plus, donc ne vont plus en tas (un tas existant reste, on n'en reprend plus) ; celles du normal (60 kg) se portent et s'empilent.
- Rouler (`roll` d'un objet de `props.json` : `axis` `ew` ou `ns`, `sheet` la planche animée `<…>-roll` de 4 images = un tour, `into` l'objet ordinaire que devient la pièce du tronc qui se met à rouler) : `systems/roll.ts`, constantes `ROLL` de `config.ts` (`startMs` 300, `minFactor` 0,15, `maxFactor` 0,6), vitesse = marche × (1 − masse / `roll`) bornée, rien ne bouge au-delà de `roll`. L'image de la planche se déduit de la position (`GameMap.rollFrame`), la bille se déplace par `GameMap.moveProp` et sa position, au pixel, est notée par `changeSpawned` / `changeObject` (pas de nouveau champ : `SAVE_VERSION` inchangée). La pose de Xéros qui pousse : animations `push-idle-*`, `push-walk-*` (posture `push`, `Player.pushing`). Une bille posée nord-sud est un objet à part (`<…>-felled-log-ns`) ; reprise, c'est la bille ordinaire tournée.
- Récolte : un objet de `props.json` avec un composant `harvest` (`tool` : objet de `items.json` de type `tool`, absent = à la main avec E ; `hits` ; `fall` : planche et animation de fin, dessinée vers la droite, avec son décalage `x`, `y` par rapport à l'objet et `foot`, la colonne du pied : l'objet tombe du côté opposé à Xéros, et vers la gauche le jeu retourne la chute et le remplaçant autour du pied ; `becomes` : objet qui le remplace, à `at` près ; `drops` : `item`, `min`, `max`, et `give` pour le mettre directement dans les mains au lieu de le lâcher au sol (le billot refuse si les mains ne sont pas libres) ; `spawns` : objets qui naissent à la fin, posés par rapport à l'objet pour une chute vers la droite et retournés autour du pied vers la gauche ; `gesture` : `use`, de côté, sur ce qui est debout, ou `chop`, de haut en bas, sur ce qui est couché ou posé). `aim` (dans l'objet) : le point visé, l'encoche d'une section de tronc ; Xéros vise ce point et l'invite s'y affiche (« Espace » quand l'outil en main convient). `impact` : matière frappée (`wood`, `stone`, `leaves`), dont les éclats (planche `fx-<matière>`, 4 variantes 8×8) jaillissent à chaque coup. Un seul système pour tout : `systems/harvest.ts`. L'objet tremble à chaque coup ; sans le bon outil, un message court le dit.
- Gestes d'outil : une entrée de `gestures.json` par geste (`use`, `chop`). Le corps joue `<geste>-<direction>` (4 images, la gauche en miroir) ; l'outil en main est l'animation `<geste>-down/up/right` de la planche `tool-<objet>`, prise du manche au centre de chaque image, posée sur la main d'après les poses du geste (`dx`, `dy` depuis les pieds, `behind`, `ahead` : l'outil passe devant ce qui est frappé au sud des pieds ; `impact` = l'image où le coup porte ; `strike` = où tombe le fer à l'impact, par rapport aux pieds : c'est lui que Xéros aligne sur l'encoche). Le jeu prend les images d'outil par nom d'animation. **Ajouter un outil = ses cinq dessins de base dans `art/items/held.ts`**. Règle : coup horizontal (`use`, de côté sur ce qui est debout), la caméra voit la face de l'outil, de profil (`diag`, `upright` : pour la hache, un seul fer en éventail, talon court et carré, fer presque noir avec un fil clair, référence `docs/references/hache-vue-de-cote.png`) ; coup vertical (`chop`, de haut en bas sur ce qui est couché), elle le voit par la tranche (`flat`, `flatDiag`, `flatEnd` : pour la hache, un bloc étroit et sombre au bout du manche, référence `docs/references/hache-vue-de-dessus.png`). `heldToolSheet` en tire toutes les poses de tous les gestes ; le champ `base` de chaque pose de `gestures.json` dit quel dessin elle utilise ; `validate.ts` exige chaque geste dans chaque planche `tool-*`. Sans planche, le geste se joue mains vides.
- **Trois arbres, deux sortes** (CONCEPTION, *Abattre un arbre*) : les gros (`big-…`, tronc de 55 cm, billes de 95 × 65 cm, à fendre plus tard) : le gros grand `big-tree` (forêt, 4 billes) et le têtard `big-pollard` (haies, bois de chauffage, 2 billes : il réutilise la souche, `big-felled-section-1`, `big-felled-crown` et les billes du gros grand, et n'a en propre que son arbre debout et ses deux chutes ; fiche `docs/objets/big-pollard.md`) ; et le normal (`normal-…`, tronc de 30 cm, 7 m, 5 billes de 95 × 40 cm contour compris, entières). Une seule forme de nom, `<sorte>-<pièce>` : `big-tree`, `normal-tree-stump`, `normal-tree-fall(-left)`, `<sorte>-felled-section-N`, `-crown`, `-head`, `-log(-N, -ns)`, `item-<sorte>-felled-log`, `held-<sorte>-felled-log`, genre de tas `big-logs` ou `normal-logs`. Chaque sorte a ses données (`props.json`, `piles.json`) et ses dessins, rien dans le moteur : tout ce qui suit vaut pour les trois (le têtard : 1 section et le houppier, 2 billes, 270 × 120 × 370 cm, dessiné 54 × 79 px pour 54 × 86 attendus, la hauteur étant sa longueur couchée ; dans `EXCEPTIONS` : tête stylisée, choix de Grégoire ; le normal : 4 sections et le houppier, 5 billes ; `foot` 24, chute à gauche : x' = 48 − (x + largeur − 1)). `validate.ts` applique à l'un et à l'autre la place de tomber et le gabarit (les deux y sont en règle : le gros 54 × 140 px, 270 × 270 × 565 cm, sa longueur couchée ; le normal 38 × 159, 190 × 190 × 700 cm, tronc droit, l'arbre de la charpente ; la première image de chaque chute est l'arbre debout, la dernière l'arbre couché, `arbres.png` le vérifie). Les genres de tas ne se mélangent pas : une bille du gros ne s'empile pas sur celles du normal. Fiches : `docs/objets/normal-tree.md`, `normal-felled-log.md`.
- Abattre un arbre : l'arbre (`harvest` de `big-tree`) tombe du côté opposé à Xéros, laisse sa souche et fait naître l'arbre couché : 3 sections (`big-felled-section-1..3`) et le houppier (`big-felled-crown`, la section de tête sous les feuilles), bout à bout, qui bloquent le passage. La dernière image de `big-tree-fall` est cet assemblage (`art/world/big-felled.ts`), pour que rien ne saute. Le houppier, frappé de haut en bas, lâche des branches et devient la tête nue (`big-felled-head`, même image et même place, chicots sur la pointe). Chaque pièce est exactement une future bille : son encoche est à son bout droit, pile à la jonction avec la suivante (`notch` dans `harvest`). Chaque coup creuse l'entaille (`<image>-n1`, `-n2`, puis `-cut-right` : une image par profondeur, notée dans GameState), et la pièce voisine montre alors sa face de coupe (`-cut-left`...). Un morceau séparé aux deux bouts devient sa bille (`big-felled-log-1..4`, même taille et même place que la pièce : rien ne bouge au remplacement, `validate.ts` le vérifie avec toutes les images d'état) ; la 4e encoche détache la pointe, qui donne une branche. Les pièces nées d'une même chute forment une chaîne, dans l'ordre de `spawns`. Vers la gauche, rien n'est retourné : la chute a sa planche (`big-tree-fall-left`, `fall.left` dans props.json) et chaque pièce et chaque état ont leur image `-left`, dessinée avec la lumière en haut à gauche ; seules les positions, les collisions et les points visés sont le miroir de la droite, autour du pied (`foot`). La souche ne dépend pas du côté. Pour viser une encoche, Xéros doit être collé au tronc, tourné vers lui (haut ou bas) et à moins d'une demi-section de l'encoche (`NOTCH_AIM`, config.ts). Tout objet qui peut tomber doit avoir la place de tomber des deux côtés dans la carte (chute et arbre couché compris) : `validate.ts` le vérifie et nomme la carte, l'objet et sa position.
- Bâtiments (CONCEPTION, *Construire* ; fiches `docs/objets/footing-stone.md`, `shed-post.md`, `shed-plate.md`, `shed-rafter.md`, `shed-roof.md`). Un bâtiment est un **jeu de pièces**, chacune un objet de `props.json` avec sa fiche et ses `dims`, posées dans Tiled pièce par pièce. `buildings.json` dit, pour chaque bâtiment, sa carte (`map`) et ses étapes (`steps` : `name`, `pieces`) dans l'ordre réel du chantier ; `validate.ts` vérifie que chaque pièce existe, n'est nommée qu'une fois et est posée sur la carte, et qu'une pièce de toit ne bloque pas. L'aperçu (`npm run art:preview`, `buildingPreview` de `tools/lib/composite-previews.ts`) lit la carte Tiled et montre le bâtiment monter, une étape de plus par image, à sa place. **Pièce à sa place réelle** : le bas de l'image d'une pièce est au sol, à son bord sud (sa profondeur d'affichage) ; une pièce en hauteur (sablière, chevron, toit) garde sous elle, dans son image, des rangées vides (la hauteur qui la sépare du sol), pour que Tiled la montre en place et que l'ordre d'affichage soit celui de son pied : Xéros sous la sablière basse est derrière elle, devant elle quand il est au sud. Une pièce qui relie des appuis posés au sol (sablière nord-sud, chevron, couverture) a `ground: true` dans `dims` : sa profondeur se voit à l'échelle du sol (gabarit : H + D, docs/STYLE.md section 8), projection (x, y, z) → (x, y − z). Une pièce qui dépasse à peine du sol (le dé) est `layer: floor`. Seules les pièces avec `body` bloquent le passage (les poteaux, 4 × 4 px) : on entre sous l'abri et on y pose des tas comme ailleurs. **Toits** : `roof: true` (chevrons, toit de planches) ; `systems/roofs.ts` (`Roofs`, appelé à chaque image par `WorldScene.update`, dans tous les modes) rend en partie transparentes (`ROOF.alpha`, fondu de `ROOF.fadeMs`, config.ts) les pièces de toit qui cachent Xéros (ses pieds dans la largeur de l'image, au nord de son bas, assez bas pour que le toit couvre sa tête), et toutes les pièces de toit qu'elles touchent (le toit entraîne ses chevrons). **Ombre portée d'un toit** : `shadow` de la couverture (`south`, `north` : hauteur du dessus du toit à ses bords sud et nord, en cm) ; le jeu la calcule (`world/roofShadow.ts`) : l'emprise au sol du toit (`dims.w` × `dims.d`, bord sud au bas de l'image), chaque bord décalé vers le sud-est selon sa hauteur et la lumière (`SHADOW` de config.ts), un parallélogramme de la couleur de l'ombre `x`, posé sur le sol (`DEPTH.shadow`), sous les poteaux et sous Xéros, et qui s'efface avec le toit ; `validate.ts` ne l'accepte que sur une pièce `roof` et `ground` ; l'aperçu woodshed-*.png la dessine par le même calcul. L'abri à bois (`woodshed`) est posé dans `ferme.tmj`, calque `abri`, à l'ouest de la porte de derrière : 4 dés, 4 poteaux de 20 × 20 cm (3 m au nord, 1,70 m au sud, 3,55 m entre les rangs : appentis à 20°), 4 sablières, 5 chevrons, le toit de planches (`shed-roof`, planches dans le sens de la pente, avant-toit visible au sud, débords de 20 cm à l'est et à l'ouest, 35 cm au nord et au sud). Rien de ce qui change en jeu : pas de GameState, construire soi-même viendra plus tard.
