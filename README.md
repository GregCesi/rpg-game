# Xéros

Jeu d'aventure en pixel art, vue de dessus. On suit Xéros, jeune paysan d'un petit village, qui découvre le monde au fil de ses péripéties. Ton médiéval fantastique, terre à terre.

Phaser 3 + TypeScript + Vite. Tuiles 32×32.

## Lancer

```bash
npm install
npm run dev            # http://localhost:5173  (?debug : collisions ; ?reset : efface la sauvegarde ; ?dieu : outils de test)
npm run art            # art/ -> PNG, manifestes et tilesets Tiled (à lancer une fois avant d'ouvrir Tiled)
npm run maps           # cartes Tiled (tiled/maps/*.tmj) -> src/generated/maps.ts
npm run sketch -- <id> # fait naître tiled/maps/<id>.tmj depuis tiled/sketches/<id>.json (grille de lettres)
npm run test           # tests : l'outil d'esquisse, puis cinq scénarios dans le vrai jeu (Chromium sans écran : npm run test:fendage, npm run test:implantation, npm run test:equarrissage, npm run test:tas, npm run test:poteaux)
npm run check          # art, maps, puis vérifie tout le contenu sans lancer le jeu (formats + références croisées)
npm run build          # check, test, puis build web dans dist/
npm run build:single   # un seul fichier HTML autonome dans dist-single/
npx tsx tools/preview-module.ts <module d'art> <dossier>  # aperçu x4 d'un seul module de dessin, sans importer tout art/ (quand plusieurs dessinateurs travaillent ensemble)
npm run art:preview    # régénère les sprites + aperçus x4 dans .art-preview/ (planche collection.png, xeros-<geste>-<outil>.png pour chaque geste et chaque outil en main, les deux mains hands.png, les tas piles.png : chaque genre écrit de piles.json, puis des tas de bois calculés de plusieurs longueurs et états (rondins, billes, quartiers tête-bêche, demi-billes, poutres, est-ouest et nord-sud), étape par étape, collisions en liseré, et pour un genre lié, le lien seul puis la construction type posée dessus ; les trois arbres à chaque étape arbres.png (debout, chute à droite et à gauche, couché tel que le jeu le pose, entaille, billes, tas : le gros grand, le têtard, puis le normal, l'un sous l'autre ; un avertissement `ATTENTION arbres` si la dernière image d'une chute n'est pas, pixel pour pixel, l'arbre couché posé), le bois bois.png (dont le quartier dans ses quatre positions), le fendage fendage.png : la bille, le coin planté, les trois fentes, les demi-billes, les quartiers, les outils et le tas de quartiers à côté de Xéros ; les étalons du gabarit gabarit.png : Xéros, cube de 50 cm, bille est-ouest, bille nord-sud, cylindre debout de 50 cm, et la taille attendue en liseré ; chaque plan de plans.json qui monte, étape par étape, posé sur la ferme à l'emplacement de son piquet nord-ouest (`PLAN_PREVIEW`, `tools/build-art.ts`) : woodshed-1.png à woodshed-5.png, woodshed-6.png Xéros dessous et le toit effacé, woodshed.png les met côte à côte)
```

Adresses de test (à combiner : `?dieu&debug`) : `?debug` montre les collisions ; `?reset` efface la sauvegarde et repart du réveil dans le cagibi (le mot est ensuite retiré de l'adresse : un rechargement reprend la nouvelle partie) ; `?dieu` ouvre à droite du jeu un panneau d'outils de test, à la souris (donner un objet en main, poser un objet du monde ou un tas devant Xéros, apprendre un plan, mettre quatre piquets ou quatre pierres plates au sol, effacer les chantiers de la carte, avec une longueur pour le rouleau de corde et un lien pour le tas de branches, aller sur une carte, remettre la carte ou la partie à zéro). Sans `?dieu`, le panneau n'existe pas.

Les cartes se font dans [Tiled](https://www.mapeditor.org/) : ouvrir `tiled/xeros.tiled-project`. Après une modification d'une carte, relancer `npm run dev` (ou `npm run maps`) pour la voir en jeu.

Commandes (touches lues par leur place sur le clavier, `KeyboardEvent.code` : même place en AZERTY et en QWERTY) : ZQSD (WASD en QWERTY) ou flèches. Maj pour courir. E (ou Entrée) : prendre dans une main libre (ramasser, prendre une bille, reprendre d'un tas, cueillir), parler, poser ce que tient la main active sur ce qui l'accepte (le rouleau sur le billot), ou, dans le vide, poser devant soi ce que tient la main active, là où le montre son fantôme (seul, contre une pièce identique où un tas naît, ou sur son tas). E maintenu une demi-seconde, mains libres, devant un tas de branches ou un fagot : nouer, dénouer (une jauge se remplit au-dessus de Xéros ; relâché avant, c'est E court). Q d'un clavier QWERTY, soit **A en AZERTY** (pour ne pas croiser le Q de ZQSD) : lâcher devant soi ce que tient la main active. Tab : changer de main active. R : tourner la pièce portée d'un quart de tour (est-ouest, nord-sud ; la face debout d'un quartier suit) ; R maintenu une seconde, mains vides, au contact d'une bille couchée : la faire pivoter d'un quart de tour. E sur la paillasse du cagibi : dormir (jauge d'endurance pleine, jour suivant). E sur la planchette gravée de la mère : apprendre le plan de l'abri. E, une pierre plate en main, sur une place en fantôme d'un chantier : la poser. Espace : utiliser ce qu'on tient (la hachette dans une main, une branche dans l'autre, face au billot : tailler un piquet ; le coin face à une grosse bille couchée : le planter ; la masse sur un coin planté : un coup ; un piquet : le planter au tracé d'un plan connu). E, Espace ou Entrée font défiler un dialogue. **Zoom** : molette (vers l'avant, on s'approche), + et − (lus par leur signe, pour qu'ils soient où ils sont imprimés sur tout clavier, ou au pavé numérique) : la caméra du monde change de palier entier (`ZOOM_STEPS` de config.ts : d'un cran sous `ZOOM` à trois au-dessus, ×1 à ×5 ; jamais de palier fractionnaire, qui rendrait le pixel art inégal), centrée sur Xéros ; une carte trop petite relève le palier le plus bas pour ne jamais montrer le vide hors d'elle (×2 pour la ferme et la maison). L'interface (cases des mains, jauge, messages, dialogues, ?dieu) a ses propres caméras et ne change pas. Le palier choisi est retenu d'une session à l'autre (`localStorage['xeros-zoom']`), hors de la sauvegarde de partie (`?reset` ne l'efface pas). `systems/zoom.ts`.

```
  world/places.ts    le moteur de places commun aux tas et aux chantiers, sans Phaser : places ouvertes, pièces à reprendre, place visée, ordre d'affichage, ce qu'une place accepte (un genre, ou une pièce précise)
  world/pileShape.ts la forme d'un tas dans son sens, son lien (les places viennent de places.ts)

  world/offer.ts     ce qu'on apporte à une place d'après ce que tient la main
  systems/           une mécanique du monde par fichier : interactions, sorties, récolte et coupe de la corde (harvest.ts), prendre, poser, les tas et le lien (hands.ts), nouer et dénouer (knot.ts), E maintenu et sa jauge (longPress.ts), nombre de pièces d'un tas (pileCount.ts), toits qui s'effacent (roofs.ts), faire rouler une bille (roll.ts), le poids des mains et les messages « trop lourd » (weight.ts), le prix des efforts et le message « épuisé » (effort.ts), pivoter une bille (turnLog.ts), les chantiers (site.ts : tracer, planter les piquets, poser les pièces, la ligne d'état), le bois (wood.ts : couper une pièce sur la grille, l'équarrir, la fendre), les fantômes en transparence (ghost.ts)...
  entities/Actor.ts  le corps d'un personnage (sprite, collision, animations)
  entities/Player.ts Actor + clavier + ToolUse + Hold
  entities/ToolUse.ts composant : le geste d'outil, l'outil posé dans la main image par image
  entities/Stamina.ts composant : l'endurance (la jauge du jour, ses dépenses, GameState en est écrit tous les points)
  entities/Strength.ts composant : la force (porter, marcher chargé, rouler), seuils de strength.json × le multiplicateur de ?dieu
  entities/Hold.ts   composant : ce qu'il tient se voit sur lui (posture du corps, objet posé au point d'accroche image par image)
  entities/Npc.ts    Actor + contrôleur immobile : un personnage non joueur qui se tourne vers Xéros quand il lui parle
  input/             lecture du clavier
  dieu/panel.ts      outils de test (?dieu) : panneau HTML hors du canevas, qui envoie des commandes à WorldScene
  scenes/            Boot (chargement), World (la carte en jeu), Hud (les deux mains, messages courts), Dialogue (par-dessus le monde)
```

### Comment tourne une image du monde

`WorldScene` assemble la carte, le joueur et les systèmes, puis arbitre selon son **mode** (`play`, `use`, `dialogue`, `transition`) : un seul à la fois. Chaque système fait une chose et rend son résultat à la scène (`InteractionSystem` dit quel objet a été utilisé, `findExit` dit quelle sortie est prise) ; c'est la scène qui décide quoi en faire. Une nouvelle mécanique = un fichier dans `systems/` + quelques lignes dans `WorldScene.update`.

Entre scènes, on passe par le bus du jeu avec les noms de `events.ts` (ex. `GameEvent.DialogueEnd`, `GameEvent.HandsChanged`, `GameEvent.Notice`). À l'intérieur d'une scène, pas d'événements : des appels directs, plus faciles à suivre.

### L'état de la partie

Les cartes décrivent le monde au début de la partie ; `GameState` (`src/state/`, schéma Zod, indépendant de Phaser) dit ce qui a changé : les **deux mains** (`hands` : gauche et droite, chacune un objet ou rien ; `both` : ce qu'on tient à deux mains ; `active` : la main qui utilise et qui lâche ; un objet tenu est un objet possédable `{ item }` ou un objet du monde pris sur la carte `{ prop, flip }`, la bille), les objets de carte changés, rangés par carte et par **identifiant d'objet Tiled** (« objet 12 de la ferme : devenu `big-tree-stump` »), les objets posés au sol, par carte, et les **objets nés** pendant la partie (les pièces d'un arbre couché), par carte, avec leur identifiant propre, et les **tas** (`piles` : genre, point au sol, places prises, sens, lien), par carte, et les **chantiers** (`sites` : plan, piquet nord-ouest, coins plantés, né ou non, pièces posées avec l'objet né qui les montre), par carte, avec les **plans connus** (`knownPlans`) ; un objet changé ou né peut être retourné (`flip`, ce qui est tombé vers la gauche) et porter une **longueur** (`length`, en cm : le rouleau de corde, ou le billot qui le porte), que garde aussi ce qu'on tient. La construction d'une carte (`GameMap`) applique ses changements et repose les objets nés. On le modifie par les fonctions de `state/GameState.ts` (`take`, `release`, `switchHand`, `changeObject`, `dropItem`, `spawnObject`, `changeSpawned`, `startPile`, `fillPlace`, `emptyPlace`, `addPile`, `removePile`, `setPileTie`, `learnPlan`, `startSite`, `plantSiteStake`, `pullSiteStake`, `placeSitePiece`, `removeSite`, `turnHeld`, `emptyHands`, `resetMap`, `replaceState`...), jamais à la main depuis une scène : chacune avance un compteur de changements (`revisionOf`), et c'est lui qui déclenche la sauvegarde.

### La sauvegarde

La partie se sauvegarde toute seule, dans le navigateur (`localStorage['xeros-partie']`, `state/save.ts`) : `{ version, savedAt, where, state }`, `where` étant la carte, les pieds et la direction de Xéros, `state` le `GameState` tel quel. `systems/autosave.ts`, appelé au début de chaque `WorldScene.update`, l'écrit dès que le compteur a bougé (objet pris, posé, coupé, tas modifié...) ; la scène l'écrit aussi à l'arrivée sur une carte et quand la page se cache ou se ferme (`pagehide`, rechargement compris), pour garder la dernière position. Une position dans une zone de sortie (`exitAt`, `systems/exits.ts`) ne s'enregistre pas telle quelle : c'est le point d'arrivée de cette sortie, sur sa carte, qui est noté, pour que Xéros ne change pas de carte tout seul au rechargement. Au lancement, `BootScene` appelle `resumeGame` (`state/index.ts`) : la partie reprend à la position exacte (`at` de `WorldStart`), sinon au réveil (`START`). La lecture (`readSave`) ne plante jamais : sauvegarde illisible, d'une autre version (`SAVE_VERSION`), refusée par `SaveSchema`, ou qui nomme une carte, un objet ou une place de tas disparus du contenu : elle est mise de côté dans `localStorage['xeros-partie-abimee']` (détail en console), le HUD le dit en clair et la partie est neuve. **Changer le format de `GameState` d'une façon que l'ancien ne lit plus = augmenter `SAVE_VERSION`** (les anciennes sauvegardes sont alors refusées proprement). `?reset` passe par `clearSave`. La future sauvegarde au cagibi utilisera les mêmes fonctions.

### Les outils de test (`?dieu`)

`main.ts` ne charge `dieu/panel.ts` qu'avec `?dieu` et le monte à droite du canevas (`#stage` de `index.html`). Le panneau ne touche pas la partie : chaque bouton envoie une `DieuCommand` (`events.ts`) sur `GameEvent.Dieu`, que `WorldScene.dieu` exécute par les fonctions de `GameState`, donc tout est sauvegardé comme en jeu (refusé hors du mode `play`). Donner en main vide d'abord les mains (ce qu'elles tenaient disparaît) ; un objet qui a une longueur (le rouleau de corde, ou le billot qui le porte) se donne ou se pose avec la longueur choisie, en mètres ; un tas d'un genre lié (les branches) se pose « avec lien », de 0 pièce (le lien seul) au tas plein ; poser un objet du monde ou un tas (un genre écrit, ou « Poser en tas » d'une pièce de bois choisie, refusé au-dessus de 70 kg) passe par `HandsSystem.placeInFront` et `pileInFront` (même place libre que pour poser à la main ; le tas met toute son emprise au sol devant Xéros, places prises du bas vers le haut) ; aller sur une carte mène à son premier point d'apparition ; remettre la carte à zéro (`resetMap`) recharge la carte autour de Xéros ; réinitialiser la partie (« Toute la partie », à confirmer : le premier clic change le bouton en « Vraiment ? », le second agit ; sans second clic, il revient au bout de 3 s) efface la sauvegarde et repart du réveil. Les listes du panneau se lisent dans `props.json`, `items.json` et `piles.json` : le têtard (`big-pollard`), l'arbre normal (`normal-tree`), son tronc couché (sections, houppier, tête), ses billes (à porter) et son genre de tas (`normal-logs`) y sont d'office, comme ceux du gros, sans code de plus. Nouvel outil de test = une variante de `DieuCommand`, un bouton dans le panneau, un cas dans `WorldScene.dieu`. Pour l'implantation : `learn-plan` (`GameState.learnPlan`), `supply` (met `count` exemplaires d'un objet possédable ou d'un objet du monde en rangée devant Xéros : `HandsSystem.supplyAround`), `erase-sites` (`SiteSystem.erase`).

### Les quatre règles

1. **Le contenu est de la donnée.** Une carte (un fichier Tiled), une tuile, un objet, plus tard une quête ou un dialogue : un fichier de données, pas une classe. Le moteur reste petit.
2. **Le pixel art est du texte.** Chaque sprite est une grille de caractères dans `art/`, convertie en PNG au build. On peut remplacer un PNG par un dessin fait à la main sans toucher au jeu : le jeu ne connaît que les clés (`xeros`, `world`, `big-tree`...).
3. **Composer plutôt qu'hériter.** Un personnage = un `Actor` (le corps) + un contrôleur (clavier, IA de PNJ). Les capacités (geste d'outil `ToolUse`, objets tenus `Hold`, plus tard stats, dialogue) sont des composants attachés, pas des sous-classes.
4. **Erreurs lisibles.** Une carte mal saisie ou un sprite de mauvaise taille doit planter avec un message qui dit où (la carte, l'objet, sa position). Les formats sont décrits une fois dans `content/types.ts` (Zod) ; la partie du format Tiled que l'on lit est décrite dans `tools/lib/tiled-schema.ts` et contrôlée par `build-maps` ; les liens entre fichiers sont vérifiés dans `content/validate.ts`, par `npm run check` et au démarrage du jeu (la liste des problèmes s'affiche à l'écran). Nouveau champ ou nouveau lien = on l'ajoute là.

### Conventions

- Animations : `<skin>-<état>-<direction>`, ex. `xeros-walk-left`. Directions : `down`, `up`, `left`, `right`.
- Ordre d'affichage : profondeur = position y des pieds (le joueur passe derrière un arbre). Les profondeurs fixes (sol, pénombre, lueurs, invite) sont dans `DEPTH` (`config.ts`).
- Collisions : toujours au niveau des pieds, jamais sur le sprite entier.
- Cartes : un fichier Tiled `tiled/maps/<id>.tmj` (l'id est le nom du fichier). Un calque de tuiles `ground` (le sol, toutes les cases peintes) et des calques d'objets au nom libre : c'est le **type** de chaque objet qui dit ce que c'est (`Spawn`, `Exit`, ou un objet de `props.json`). Propriétés de la carte : `name` (nom affiché) et `ambient` (pénombre des intérieurs, de 0 à 1). Le jeu de tuiles (`world` ou `interior`) se déduit du `.tsj` que la carte référence : un seul par carte, plus le tileset `props` pour poser les objets. Tuiles retournées, pivotées, intégrées ou redimensionnées : refusées avec un message.
- Nouvelle carte : on **esquisse**, puis on retouche dans Tiled. `tiled/sketches/<id>.json` décrit la carte en lettres (sol et objets, une lettre par case, `spawns` et `exits` en cases : l'ancien format de carte) ; la légende des lettres (lettre de sol -> tuiles ou terrain à raccord automatique, lettre d'objet -> clé de `props.json` et ancrage `center` ou `left`) est dans `tiled/sketch-legend.json`. `npm run sketch -- <id>` écrit `tiled/maps/<id>.tmj` (raccords automatiques, variantes au hasard stables, objets ancrés), puis on ouvre le résultat dans Tiled (`open -a Tiled tiled/xeros.tiled-project tiled/maps/<id>.tmj`). L'outil refuse d'écrire si le `.tmj` existe : l'esquisse ne sert qu'à la naissance, ensuite c'est le `.tmj` qui fait foi (les esquisses ne sont pas committées). Une lettre inconnue donne un message avec la lettre et sa position. `npm run test`, lancé par `npm run build`, repasse les anciennes cartes ferme et maison (fixtures) dans l'outil et exige les mêmes calques, objets, points et sorties que des copies figées de leurs `.tmj`.
- Le sol est peint avec son rendu final (pinceau terrain de Tiled) : le jeu affiche les tuiles telles quelles. Seuls les détails au hasard (touffes, paille…, `decals` de `tiles.json`) sont posés en jeu, de façon stable.
- Objets : type = clé de `props.json` (identifiant anglais en kebab-case : `big-tree`, `woodpile` ; son champ `name` est le nom affiché, en français), position au pixel (coin bas gauche de l'image : c'est aussi la profondeur d'affichage). Champ `interact` facultatif pour changer le dialogue de cet exemplaire.
- Points d'apparition : un point de type `Spawn`, son **nom** est son identifiant, `facing` facultatif. Position = les pieds du joueur.
- Personnages non joueurs : un point de type `Npc` (position = ses pieds), propriétés `character` (clé de `characters.json`, qui est aussi la clé de son sprite : il lui faut les animations `idle-down/up/left/right`), `dialogue` (clé de `dialogues.json`) et `facing` facultatif (`down` par défaut). Il est immobile, bloque le passage par ses pieds, se tourne vers Xéros pendant le dialogue puis reprend sa direction. `build-maps` le traduit en `npcs` de la carte ; `validate.ts` vérifie le personnage, le dialogue et les animations (message : carte, personnage, position). Pas encore de déplacement ni de journée type : un contrôleur d'IA viendra se brancher sur le même `Actor`.
- Sorties : un rectangle de type `Exit` (`to` = carte, `spawn` = point d'arrivée, `facing` facultatif). On la prend quand les pieds sont dedans, en avançant dans la direction `facing` si elle est donnée. C'est le premier type de zone ; d'autres suivront.
- Les tilesets de `tiled/tilesets/` et le fichier projet sont **générés** par `build-art` : on ne les modifie jamais dans Tiled (ils seraient réécrits). Pour changer une tuile ou un objet : `art/`, `tiles.json` ou `props.json`, puis `npm run art`.
- Numéros de tuiles : `art/tile-registry.json` (committé) donne à chaque tuile sa place, et les `.tmj` stockent ces numéros. Une tuile nouvelle est ajoutée en fin de liste par `npm run art` (committer le fichier) ; une tuile retirée de `art/` laisse un trou et ne peut plus être posée ; ne jamais réordonner. Renommer une tuile = changer son nom dans le registre **et** dans `art/`, à la même position.
- Départ de la partie : `START` dans `config.ts` (une partie sauvegardée reprend là où elle était, voir *La sauvegarde*).
- Raccords automatiques : clôtures, chemins, eau et cloisons (intérieur) sont des **terrains** (`terrains` de `tiles.json`) : une famille de 16 tuiles `<terrain>-<masque>` (masque N=1 E=2 S=4 O=8, un bit à 1 = le voisin est du même terrain). Dans le tileset de Tiled, chacun devient un ensemble Wang de type bord à deux couleurs : le terrain et « autre ». Une arête à 0 voudrait dire « indifférente » pour Tiled : elle n'est jamais utilisée, une arête absente du masque prend la couleur « autre », et les 16 `wangid` sont tous différents (vérifié par `build-art`). Limites connues : la cloison ne se raccorde pas d'elle-même aux murs, on pose la tuile d'accroche à la main ; en bord de carte, c'est le pinceau de Tiled qui choisit la tuile (une arête sans voisin), alors que l'ancien code comptait « hors de la carte » comme du même terrain : vérifier à l'œil les chemins qui sortent de l'écran.
- Objets (`props.json`) : `dims` (obligatoire) donne ses dimensions réelles en centimètres (`w` largeur, `d` profondeur, `h` hauteur, `shape` : `box`, `cylinder` avec `axis` `ew`/`ns`/`up`, ou `flat`) ; `validate.ts` en tire la taille attendue de sa silhouette d'après le gabarit (`src/content/gabarit.ts`, docs/STYLE.md section 8 : 5 cm par pixel, dessus et faces en raccourci à ½) et refuse un écart de plus de 2 px, sauf pour les objets anciens de `EXCEPTIONS` (`validate.ts`). La silhouette (pixels opaques, contour compris, ombre exclue) est calculée par `build-art` et notée dans le manifeste. `bodies` pour des collisions de forme libre, `anim` pour un objet animé (feu), `smoke` et `light` pour la fumée et les lueurs. Les collisions restent ici, pas dans Tiled.
- Tuiles (`tiles.json`) : `solid` (bloque le passage), `decals` (nom d'un ensemble de détails au hasard) et `terrains`. Les propriétés `solid` et `decals` apparaissent aussi comme propriétés de tuile dans le tileset de Tiled.
- Interactions : un objet de `props.json` avec `"interact": "<id>"` lance le dialogue `<id>` de `dialogues.json`.
- Objets possédables (`items.json`) : clé en anglais kebab-case, `name` en français, `icon` (`item-<clé>`, 16×16, dans les cases des mains), `ground` facultatif (son image couchée au sol, à l'échelle ; sinon l'icône : la branche a `branch-ground`, le même dessin que dans le tas et en main, `art/items/branch.ts`), `kind` (`tool`, `weapon`, `resource`), `hands` (1 par défaut, 2 pour ce qui est lourd ou long : la hache). Une main tient un seul objet ; pas de besace. Un objet au sol se prend avec E dans une main libre (les deux s'il le demande) ; sinon « Les mains pleines. ».
- Les deux mains : E prend dans une main libre (la main active si elle est libre), ou, quand les deux mains tiennent un seul objet, le repose devant soi (E ne vise alors que les personnages à qui parler) ; Q (A en AZERTY) lâche devant soi ce que tient la main active ; Tab change de main active ; quand la main active se vide (posée, lâchée, piquet ou coin planté, lien utilisé...) et que l'autre tient un objet, la main active passe sur l'autre, comme Tab (une seule règle, `followHeld` de `state/GameState.ts`, appelée par `release` et `clearHeld`) ; Espace utilise ce qu'on tient (la hache à deux mains s'utilise). On ne pose qu'à une place libre devant soi (dans la carte, hors cases bloquantes, collisions d'objets et personnages ; sinon « Pas la place ici. »). Un objet possédable posé reste au sol (GameState, `ground`). Le tout : `systems/hands.ts` ; à l'écran, deux cases G et D, la main active marquée ; une main vide montre une main ouverte (`ui-hand-left`, `ui-hand-right`) ; ce qu'on tient à deux mains s'affiche dans la case droite, la gauche montrant `ui-hands-both`.
- Objets du monde à prendre : un objet de `props.json` avec un composant `take` (`hands` : 1 ou 2 ; `icon` : son icône dans les cases des mains ; `hold` : comment il se voit tenu). Ni `harvest` ni `interact` avec (validate.ts). Pris avec E, il quitte la carte (GameState : objet né retiré, objet de Tiled noté disparu) ; posé, il revient comme objet né, à sa nouvelle place, et s'y retrouve après un changement de carte (sauf s'il s'entrepose, `pile` : il va alors en tas, voir Tas). Les billes de l'arbre normal se prennent à deux mains et se portent devant lui ; celles du gros arbre (214 kg à 1 m) sont trop lourdes pour les 70 kg de Xéros : elles se roulent.
- Poser et les tas (CONCEPTION, *Les tas*, repris le 30 octobre 2026). **Un seul chemin de pose** pour tout ce qu'on porte (`systems/hands.ts` : `dropTarget` dit où, `ghostOf` le fantôme, `put` pose) : E dans le vide ou Q, là où le montre le fantôme (caché quand E vise une cible) ; le lien sous un tas de son genre ou par terre ; ce qui va en tas à la place la plus proche du point que regarde Xéros, à portée (`INTERACT.radius`), parmi les places d'un tas qui entrepose la même chose et celles d'un tas qui naîtrait d'une pièce identique seule au sol (elle en devient la première pièce, à sa place exacte, et donne au tas son sens) ; sinon seul, devant Xéros, ou à la place libre la plus proche à côté (`PUT_DOWN.step`, `reach`) ; sinon « Pas la place ici. ». **Ce qu'entrepose un tas** (GameState, `piles` de la carte) : un genre écrit (`pile`, clé de piles.json : branches, fagots) ou une pièce de bois (`wood` : diamètre, forme, longueur, coups de doloire) ; `pileDefOf(kindOf(tas))` et `shapeOf(def, turned)` (`world/pileShape.ts`) donnent sa forme. **Tas de bois calculés** (`world/woodPile.ts`) : seule une pièce sans coupe ni coin, de 70 kg au plus (`carry` de strength.json), va en tas (`pileWoodOf`) ; les identiques (`sameWood`) s'y ajoutent ; la forme vient de la section (`woodBody`, `woodDims`) : pyramide g0 g1 g2, u01 u12, top pour le rond (et f1 à f3), rangées g0 g1 g2, l1-0..., l2-2 pour la demi-bille, le quartier (tête-bêche, `face` alternée) et la poutre ; chaque place montre la pièce assemblée à sa longueur (`GameMap.placeImage`, `woodTexture`). **Genres écrits** (`piles.json`) : `piece` (`item` ou `prop`), `start`, `blockFrom` (3 pour les branches), `order` (`layers` par défaut, `depth` de l'arrière vers l'avant), `places` (`layer`, `on`, `image`, `x`, `y`, `body` au sol, `aim`), `turned` (forme nord-sud : le fagot), `tie`, `count` ; `validate.ts` vérifie la pièce reprise, la place de départ, les images, les collisions au sol et les porteuses, et refuse un tas de bois écrit. Une place au sol ne s'ouvre qu'en touchant une pièce déjà posée au sol. E, mains libres, reprend la pièce la plus haute (dans le sens et la face de sa place) ; le tas disparaît à la dernière. Le tout : `systems/hands.ts`, `GameMap.placePile` (affichage, collisions), `world/places.ts`, `world/pileShape.ts`. Aperçu : `.art-preview/piles.png`. Test : `npm run test:tas`.
- Corde, lien et fagot (fiches : `docs/objets/rope-coil.md`, `rope-tie.md`, `faggot.md`). **Quantité mesurée** : un objet de `props.json` avec `length` (`start`, longueur neuve en cm ; `cut`, ce qu'enlève une coupe ; `piece`, l'objet possédable qui tombe à chaque coupe) garde sa longueur restante dans GameState (`length` de ce qu'on tient, de l'objet né ou changé). Le rouleau de corde (`rope-coil`, 10 m, une main) est posé dans la réserve de `maison.tmj` ; il ne se range pas en tas ; tenu, sa longueur restante s'écrit en petit en bas de sa case de main (HudScene, signes `ui-digit-<chiffre>`, `ui-digit-comma`, `ui-digit-m`). **Poser sur** : `rest` d'un objet (`{ "<objet tenu>": "<ce qu'il devient>" }`) : E, l'objet tenu dans la main active, face à lui ; ce qu'il devient a `bears` (`prop`, l'objet porté, `empty`, ce qu'il redevient) : E, mains libres, reprend l'objet porté avec sa longueur, et son `harvest` (outil, geste ; `also` : d'autres outils qui font le même travail, chacun avec le prix de son coup, la hachette à 0,4 point comme la cognée à 0,5) le coupe : chaque coup enlève `cut`, lâche `piece` au sol, et, vide, l'objet porté disparaît (`HarvestSystem.cutBorne`, message « Rouleau de corde : 8 m restants. »). Le billot : `chopping-block` + rouleau = `chopping-block-rope`, la hachette ou la cognée coupe un lien (`rope-tie`, 2 m). **Lien d'un tas** : `tie` d'un genre de `piles.json` (`item`, l'objet possédable qui lie ; `north` et `south`, ses deux bouts courts qui dépassent sous le tas, chacun `image`, `x` et `dy` : le bout nord accroché au bord nord de la pièce au sol la plus au nord, le sud au bord sud de la plus au sud, pour qu'ils suivent la taille du tas, `tieImages` de `world/pileShape.ts` ; `alone`, son dessin seul par terre, une boucle lâche, coin bas gauche dans le repère du tas ; `into`, ce que devient le tas plein et lié une fois noué). Q d'un lien : sous le tas de ce genre sans lien le plus proche, à portée (il le ceinture par-dessous), sinon par terre devant Xéros, où il commence un tas sans pièce (GameState : `tie` du tas, `places` vide) ; le fantôme le montre. Le lien se dessine sous toutes les pièces. E sur un tas lié sans pièce reprend le lien. **Nouer, dénouer** (`systems/knot.ts`, E maintenu, mains libres) : un tas plein et lié devient un tas d'une pièce de `into` (le fagot), centré à sa place ; un fagot seul (tas d'une pièce, ou posé hors d'un tas) redevient le tas plein lié de son genre ; sinon « Il faut un lien. », « Pas assez de branches. », « Un seul fagot à la fois. », « Pas la place ici. ». **E maintenu** (`systems/longPress.ts`, `LONG_PRESS` de config.ts) : devant une cible que `KnotSystem.holds` reconnaît, l'appui attend ; relâché avant 500 ms, c'est E court (reprendre une pièce, le fagot), tenu jusqu'au bout, le geste long ; la jauge `ui-gauge` (animation `fill`) se remplit au-dessus de la tête ; Xéros qui vise autre chose abandonne l'appui. **Fagot** (`faggot`, 130 × Ø 50 cm, deux mains, `carry`) : genre `faggots`, même forme que les billes (6), tourné nord-sud (`faggot-ns`) avec R. **Nombre de pièces** : `count` d'un genre (les branches) : en tout petits chiffres (`ui-digit-<n>`) en bas à droite du tas, quand les pieds de Xéros sont à moins de `PILE_COUNT.near` px de ses pièces au sol (`systems/pileCount.ts`). `validate.ts` vérifie la pièce coupée, `rest` et `bears` réciproques, le lien (objet à une main, image, genre non tourné, `into` qui s'entrepose ailleurs), la jauge et les chiffres.
- Objets tenus, visibles sur Xéros à l'attente et à la marche (composant `Hold`) : `hold` d'un objet de `items.json` ou du `take` d'un objet de `props.json` = `stance` (posture : `hand`, bras pendants, un objet par main ; `shoulder`, la hache sur l'épaule, animations `shoulder-idle/walk-*` ; `carry`, porté devant lui à deux mains, `carry-idle/walk-*`) et `image`, la planche `held-<…>` (`art/items/carried.ts` : animations `down`, `up`, `right` d'une image, point d'accroche au centre ; la bille vue par le bout de profil). Sans `hold` : l'icône dans la main (à deux mains : `carry`). `hold.json` donne, par posture, état et direction, le point d'accroche de chaque image du corps (`dx`, `dy` depuis les pieds, `behind`) ; en posture `hand`, un point par main de Xéros (`left`, `right`, tirés de `HAND_POINTS` dans `art/characters/xeros.ts`, comme `SHOULDER_POINTS` et `CARRY_HANDS`). Vers la gauche : le miroir de la droite, mains échangées (la main côté spectateur n'est plus la même). Caché pendant un geste, où l'outil du geste prend sa place. Portant à deux mains (`carry`), il marche lentement (`PLAYER.carrySpeed`), ne court pas et n'utilise rien ; la hache sur l'épaule s'utilise. `validate.ts` vérifie les animations de chaque posture, leurs nombres d'images, les trois vues des planches et que la posture va avec les mains (`hand` pour une main).
- Masses et force (CONCEPTION, *Poids et force*). Tout objet qu'on prend, pose ou roule a une masse (`mass` dans `items.json` : un nombre ; dans `props.json` : un nombre, `"wood"` pour la pièce de bois, calculée par ses réglages (*Le bois*), ou `{ "pile": genre }` pour la somme d'un tas plein et de son lien) ; `validate.ts` refuse un objet qui se prend ou roule sans masse. `src/content/mass.ts` pèse (`propMass`, `itemMass`, `heldMass`). La force de Xéros est dans `strength.json` (`carry` 70, `walk` 25, `roll` 300 kg, `slowest` 0,5) et le composant `entities/Strength.ts` (`load` = masse portée, mise à jour par `WorldScene.handsChanged`) ; E refuse ce qui dépasse `carry` (`systems/weight.ts`). Porté au-delà de `walk` : pas de course, marche ralentie jusqu'à `slowest` à `carry` (`Player.update`). Une sauvegarde qui tient trop lourd pose l'objet au sol au chargement (`WorldScene.dropHeavy`). Les billes du gros arbre (214 kg à 1 m) ne se portent plus, donc ne vont plus en tas (un tas existant reste, on n'en reprend plus) ; celles du normal (63,6 kg) se portent et s'empilent.
- Rouler (la pièce de bois ronde : `roll` de sa définition, `axis` `ew` ou `ns`) : `systems/roll.ts`, constantes `ROLL` de `config.ts` (`startMs` 300, `minFactor` 0,15, `maxFactor` 0,6), vitesse = marche × (1 − masse / `roll`) bornée, rien ne bouge au-delà de `roll` (strength.json). L'image de roulement (4 images de sa texture = un tour) se déduit de la position (`GameMap.rollFrame`), la pièce se déplace par `GameMap.moveProp` et sa position, au pixel, est notée par `changeSpawned` / `changeObject`. La pose de Xéros qui pousse : animations `push-idle-*`, `push-walk-*` (posture `push`, `Player.pushing`). Ne roulent pas : la poutre (« Elle ne roule pas : elle est carrée. »), une pièce à une face dressée, la demi-bille et le quartier (à plat), une pièce entaillée ou coin planté.
- Récolte : un objet de `props.json` avec un composant `harvest` (`tool` : objet de `items.json` de type `tool`, absent = à la main avec E ; `hits` ; `fall` : planche et animation de fin, dessinée vers la droite, avec son décalage `x`, `y` par rapport à l'objet et `foot`, la colonne du pied : l'objet tombe du côté opposé à Xéros, et vers la gauche le jeu retourne la chute et le remplaçant autour du pied ; `becomes` : objet qui le remplace, à `at` près ; `drops` : `item`, `min`, `max`, et `give` pour le mettre directement dans les mains au lieu de le lâcher au sol (le billot refuse si les mains ne sont pas libres) ; `spawns` : objets qui naissent à la fin, posés par rapport à l'objet pour une chute vers la droite et retournés autour du pied vers la gauche ; `gesture` : `use`, de côté, sur ce qui est debout, ou `chop`, de haut en bas, sur ce qui est couché ou posé). `aim` (dans l'objet) : le point visé, l'encoche d'une section de tronc ; Xéros vise ce point et l'invite s'y affiche (« Espace » quand l'outil en main convient). `impact` : matière frappée (`wood`, `stone`, `leaves`), dont les éclats (planche `fx-<matière>`, 4 variantes 8×8) jaillissent à chaque coup. Un seul système pour tout : `systems/harvest.ts`. L'objet tremble à chaque coup ; sans le bon outil, un message court le dit.
- Tailler : `convert` d'un `harvest` (`from`, `into`, `refuse`), pour un outil à une main : le coup change l'objet possédable tenu dans l'AUTRE main (`HarvestSystem.whittleHit`, `GameState.replaceHeld`), dans la même main ; `refuse` est dit, sans geste ni dépense, si l'autre main ne le tient pas. La hachette sur le billot (`chopping-block`) : la branche devient un piquet (`effort: whittle`, 0,4 point). Si la main active tient la ressource et l'autre l'outil, c'est l'outil qui sert à Espace (`WorldScene.usable`).
- Gestes d'outil : une entrée de `gestures.json` par geste (`use`, `chop`). Le corps joue `<geste>-<direction>` (4 images, la gauche en miroir) ; l'outil en main est l'animation `<geste>-down/up/right` de la planche `tool-<objet>`, prise du manche au centre de chaque image, posée sur la main d'après les poses du geste (`dx`, `dy` depuis les pieds, `behind`, `ahead` : l'outil passe devant ce qui est frappé au sud des pieds ; `impact` = l'image où le coup porte ; `strike` = où tombe le fer à l'impact, par rapport aux pieds : c'est lui que Xéros aligne sur l'encoche). Le jeu prend les images d'outil par nom d'animation. **Ajouter un outil = ses cinq dessins de base dans `art/items/held.ts`**. Règle : coup horizontal (`use`, de côté sur ce qui est debout), la caméra voit la face de l'outil, de profil (`diag`, `upright` : pour la hache, un seul fer en éventail, talon court et carré, fer presque noir avec un fil clair, référence `docs/references/hache-vue-de-cote.png`) ; coup vertical (`chop`, de haut en bas sur ce qui est couché), elle le voit par la tranche (`flat`, `flatDiag`, `flatEnd` : pour la hache, un bloc étroit et sombre au bout du manche, référence `docs/references/hache-vue-de-dessus.png`). `heldToolSheet` en tire toutes les poses de tous les gestes ; le champ `base` de chaque pose de `gestures.json` dit quel dessin elle utilise ; `validate.ts` exige chaque geste dans chaque planche `tool-*`. Sans planche, le geste se joue mains vides.
- **Trois arbres, deux sortes** (CONCEPTION, *Abattre un arbre*, *Le bois*) : les gros (`big-…`, tronc de 55 cm) : le gros grand `big-tree` (forêt) et le têtard `big-pollard` (haies, bois de chauffage ; il réutilise la souche du gros et n'a en propre que son arbre debout, ses deux chutes et son arbre couché ; fiche `docs/objets/big-pollard.md`) ; et le normal (`normal-…`, tronc de 30 cm, 7 m, l'arbre de la charpente ; fiches `docs/objets/normal-tree.md`). Une seule forme de nom, `<sorte>-<pièce>` : `big-tree`, `normal-tree-stump`, `normal-tree-fall(-left)`, `<arbre>-felled-tree(-left)` (l'arbre couché d'un seul tenant), genre de tas `big-logs` ou `normal-logs`. Le bois qui en sort n'a pas de clé à lui : ce sont des pièces de bois (voir *Le bois* plus bas) du diamètre de la sorte (le têtard donne des pièces `big`, sans rien de particulier). `validate.ts` applique aux trois la place de tomber et le gabarit (le têtard est dans `EXCEPTIONS` : tête stylisée, choix de Grégoire) ; la première image de chaque chute est l'arbre debout, la dernière l'arbre couché (`arbres.png` le vérifie).
- Abattre un arbre : l'arbre (`harvest` de `big-tree`) tombe du côté opposé à Xéros, laisse sa souche et fait naître l'arbre couché d'un seul tenant (tronc et houppier, `spawns`), qui bloque le passage ; vers la gauche, rien n'est retourné : la chute a sa planche (`fall.left`) et l'arbre couché son image `-left`, dessinée avec la lumière en haut à gauche ; seules les positions, les collisions et les points visés sont le miroir de la droite, autour du pied (`foot`). Le houppier, frappé de haut en bas (3 coups de cognée), lâche des branches, et le tronc ébranché devient une seule pièce de bois ronde de sa longueur utile (`becomes: "wood-piece"`, `wood` : son diamètre et sa longueur ; le gros grand 4 m, le têtard 2 m, le normal 5,8 m), posée exactement sur le tronc (`at`, en miroir vers la gauche). Tout objet qui peut tomber doit avoir la place de tomber des deux côtés dans la carte : `validate.ts` le vérifie.
- **Le bois** (CONCEPTION, *Le bois* ; fiche `docs/objets/wood-piece.md`). Tout le bois du monde est **un seul objet**, la pièce de bois (`wood-piece` de props.json), décrite par des **réglages** et non par des clés : `size` (le diamètre, clé de `sizes` de `src/content/wood.json` : `big` 55 cm, `normal` 30 cm), `length` (cm), `shape` (`round`, `half`, `quarter`), `hewn` (coups de doloire, une face tous les `perFace`), `axis` (`ew`, `ns`), `notch` (coupe en cours : `at`, `hits`), `wedge` (coin planté : `end`, `hits`) ; schéma `WoodPieceSchema` (`src/content/types.ts`), gardés par GameState (`wood` d'un objet né ou changé, et de ce qu'on tient), donnés dans Tiled en propriétés de l'objet (`size`, `length`, `shape`, `axis`, `hewn` ; sans : les réglages par défaut, `wood` de props.json). **Nouveau bois = un diamètre ou un aspect dans wood.json (et ses dessins), pas une nouvelle clé.** wood.json donne la densité, la grille (`grid` 20 cm : la coupe s'aimante depuis le bout le plus proche de Xéros), la plus courte pièce (`min` 60 cm : « Le bout serait trop court. »), la coupe (`cut` : la cognée, 3 coups), l'équarrissage (`hew` : la doloire, 3 coups par face, la poutre de 20 cm), le fendage (`split` : le coin, la masse, 3 coups par mètre commencé, `splitHits`, un seul coin à toute longueur) et, par diamètre, sa planche (`sheet`), sa bande d'encoche, ce qui lui est refusé (`hew` : « Trop grosse pour une poutre. »), ce qui se fend et en quoi (`split` : la bille en demi-billes, la demi en quartiers, et où naissent les deux morceaux), et ses aspects (`looks` : nom, genre, icône `item-wood-…`, vue portée `held-wood-…`, géométrie de ses parties et sa collision). `src/world/woodPiece.ts` tire des réglages la définition complète de la pièce (`woodDef` : nom, dimensions, collision, prise à deux mains, roulement s'il est rond, pivot, genre de tas), si bien que prendre, poser, rouler, pivoter et entasser la traitent comme tout objet ; `src/content/mass.ts` la pèse (`woodMass` : section × longueur × densité). Son image s'assemble à sa longueur par les opérations de `src/world/woodShape.ts` (`composeOps` : bout, milieu répété, bout ; la partie du bout du coin remplacée par `wedge-…` ; la fente `crack-…` rognée à la part fendue ; le bois ouvert `open-…` du dernier coup ; la bande d'encoche), dans les planches `<sheet>` et `<sheet>-ns` (`art/world/wood-pieces.ts`, qui en tire aussi les images de 1 m des tas, `wood-<diamètre>-<aspect>-100(-ns)`) ; le jeu les suit à la volée (`src/world/woodTexture.ts`, aussi la vue portée : par le bout de face et de dos, en long à sa longueur de profil). `systems/wood.ts` : couper à la cognée contre le flanc (la ligne « 3 m | 2,6 m » au-dessus de la coupe visée), équarrir à la doloire, planter le coin à un bout (sans geste), frapper à la masse depuis ce bout ; refus dits sans geste ni dépense. Les tas de bois se calculent (voir *Poser et les tas*). Le quartier garde le côté de sa face fendue debout (`face`, quatre dessins `quarter-<face>-…`) ; R et le pivot le tournent d'un quart de tour dans le sens des aiguilles d'une montre (`turnedWood`) ; le fendage d'une demi-bille donne deux quartiers faces opposées (`splitPieces`). `validate.ts` vérifie au gabarit la demi-bille, le quartier et la poutre assemblés à plusieurs longueurs (`woodSilhouettes` du manifeste). `validate.ts` vérifie les planches de chaque diamètre et aspect, icônes, vues portées, outils, la grille, les tas et les récoltes qui donnent du bois. Aperçu : `.art-preview/bois.png`. Tests : `npm run test:fendage`, `npm run test:equarrissage`.
- Bâtiments (CONCEPTION, *Construire* ; fiches `docs/objets/footing-stone.md`, `shed-post.md`, `shed-plate.md`, `shed-rafter.md`, `shed-roof.md`, et pour l'implantation `plan-tablet.md`, `stake.md`, `hatchet.md`, `flat-stone.md`). Un bâtiment est un **jeu de pièces**, chacune un objet de `props.json` avec sa fiche et ses `dims`, et **un plan** : `src/content/plans.json`, en centimètres. **Un nouveau bâtiment = un plan, sans code nouveau.** Un plan dit son nom et ce que dit Xéros en l'apprenant (`learned`), le piquet qui trace son emprise (`stake`, objet possédable) et l'objet qui le montre planté (`planted`), l'orientation (`facing` : le côté haut du toit au nord, seul sens dessiné), l'emprise entre les axes des coins (`footprint`) et ses quatre `corners` depuis le piquet nord-ouest, puis ses `steps` dans l'ordre réel du chantier : chacune a un `name` (« les dés »), des `places`, un `accepts` par défaut (`prop` ou `item` : la pièce qu'on apporte, `refuse` : ce qu'on dit sinon) et `soon: true` si elle est « à venir ». Une place : `piece` (l'objet de `props.json` qui paraît sur la carte), `at` (cm depuis le piquet nord-ouest : le coin bas gauche de son image), `orientation`, `on` (les places d'étapes d'avant sur lesquelles elle repose), `corner` (le piquet de ce coin est arraché quand elle est posée), `accepts` (autre chose que l'étape). `validate.ts` vérifie le plan (coins, noms, `on`, piquet), et pour une étape ouverte les pièces, ce qu'elle accepte (existe, se prend, se porte) et le message ; les étapes `soon` seront vérifiées quand elles s'ouvriront. L'aperçu (`npm run art:preview`, `buildingPreview` de `tools/lib/composite-previews.ts`) pose chaque plan sur la ferme et le montre monter, une étape de plus par image. **Tracer et bâtir en jeu** (`systems/site.ts`, `world/sitePlan.ts`) : E sur une planchette (`teaches` d'un objet de `props.json` : la clé du plan) apprend le plan (GameState : `knownPlans`) ; Espace avec le piquet d'un plan connu le plante (le premier fixe le coin nord-ouest du tracé, les autres ne se plantent qu'aux coins en fantôme, `SITE.snap` px de tolérance ; E reprend un piquet tant que le chantier n'est pas né ; le quatrième fait naître le chantier si toute l'emprise est libre, sinon « Il y a quelque chose dans le passage. ») ; le chantier est un `Site` de GameState (`sites` de la carte) ; il montre en fantôme les places de l'étape en cours (la visée en met une en avant quand ce qu'on tient lui convient), E avec la pièce attendue la pose (un objet né à la place du plan, noté dans `placed`), arrache le piquet de son `corner` (il retombe au sol), et la ligne d'état « Abri à bois : dés, 2 sur 4 » paraît quand Xéros est près (`SITE.near`) ; une pièce que la place n'accepte pas est refusée avec le message du plan. Une étape `soon` montre ses places, mais n'accepte rien (« Cette étape viendra plus tard. »). **Pièce à sa place réelle** : le bas de l'image d'une pièce est au sol, à son bord sud (sa profondeur d'affichage) ; une pièce en hauteur (sablière, chevron, toit) garde sous elle, dans son image, des rangées vides (la hauteur qui la sépare du sol) : Xéros sous la sablière basse est derrière elle, devant elle quand il est au sud. Une pièce qui relie des appuis posés au sol (sablière nord-sud, chevron, couverture) a `ground: true` dans `dims` : sa profondeur se voit à l'échelle du sol (gabarit : H + D, docs/STYLE.md section 8), projection (x, y, z) → (x, y − z). Une pièce qui dépasse à peine du sol (le dé) est `layer: floor`. Seules les pièces avec `body` bloquent le passage (les poteaux, 4 × 4 px) : on entre sous l'abri et on y pose des tas comme ailleurs. **Toits** : `roof: true` (chevrons, toit de planches) ; `systems/roofs.ts` (`Roofs`, appelé à chaque image par `WorldScene.update`, dans tous les modes) rend en partie transparentes (`ROOF.alpha`, fondu de `ROOF.fadeMs`, config.ts) les pièces de toit qui cachent Xéros (ses pieds dans la largeur de l'image, au nord de son bas, assez bas pour que le toit couvre sa tête), et toutes les pièces de toit qu'elles touchent (le toit entraîne ses chevrons). **Ombre portée d'un toit** : `shadow` de la couverture (`south`, `north` : hauteur du dessus du toit à ses bords sud et nord, en cm) ; le jeu la calcule (`world/roofShadow.ts`) : l'emprise au sol du toit (`dims.w` × `dims.d`, bord sud au bas de l'image), chaque bord décalé vers le sud-est selon sa hauteur et la lumière (`SHADOW` de config.ts), un parallélogramme de la couleur de l'ombre `x`, posé sur le sol (`DEPTH.shadow`), sous les poteaux et sous Xéros, et qui s'efface avec le toit ; `validate.ts` ne l'accepte que sur une pièce `roof` et `ground` ; l'aperçu woodshed-*.png la dessine par le même calcul. L'abri à bois (`woodshed`) n'est plus posé dans `ferme.tmj` : 4 dés, 4 poteaux de 20 × 20 cm (3 m au nord, 1,70 m au sud, 3,55 m entre les rangs : appentis à 20°), 4 sablières, 5 chevrons, le toit de planches (`shed-roof`, planches dans le sens de la pente, avant-toit visible au sud, débords de 20 cm à l'est et à l'ouest, 35 cm au nord et au sud) sont les places de son plan ; seule l'étape des dés est jouable pour l'instant (six pierres plates sur la berge de l'étang, à l'ouest de la ferme ; la planchette est sur la table de la chambre de la mère).
- Moteur de places (`world/places.ts`, sans Phaser), commun aux tas et aux chantiers : des places avec une couche et des porteuses (`on`) ; `placeOpen`, `openPlaces`, `freePieces`, `topPieces` (la plus haute qu'on reprend), `placeAim`, `nearestOpenPlace` (la place visée, à portée), `drawOrder`, `placeStates` ; et ce qu'une place accepte, `Accepts` : un genre de tas (`genre`) ou une pièce précise (`prop`, `item` ; plus tard des mesures), avec `accepts` et `refusal` (le message) ; `world/offer.ts` dit ce que présente ce qu'on tient. Le fantôme (une pièce en transparence là où elle ira) est `systems/ghost.ts`. `world/pileShape.ts` reprend les noms d'avant pour les tas (`openPlaces`...), et ajoute ce qui est propre au tas (`shapeOf`, `tieImages`, `pileBlocks`). Les tas marchent comme avant : `npm run test` (fendage : tas de quartiers) et `?dieu` (poser un tas) le montrent.
- Dialogues : chaque ligne a un `speaker` (clé de `characters.json`), une `expression` et un `text`. Le portrait affiché est `portrait-<portrait>-64` (une seule taille, `PORTRAIT_SIZE` dans `config.ts`) avec l'animation `<expression>`.
- Rendu : le canvas fait VIEW × ZOOM ; les caméras de l'interface zooment de ZOOM, celle du monde du palier choisi (`ZOOM_STEPS`, systems/zoom.ts) ; le texte posé dans le monde (ligne d'état d'un chantier) est rendu à la résolution du plus haut palier. Le pixel art garde sa taille, le texte reste net.
