# Xéros — consignes pour les agents de code

Lis `README.md` (architecture et quatre règles) avant toute modification, et `docs/CONCEPTION.md` (univers, personnages, lieux, feuille de route) avant tout travail sur le contenu.

## Façon de travailler (voulue par Grégoire : les erreurs coûtent cher)

1. **Le cadrage** : lire ce qu'il faut, puis dire point par point ce qu'on va faire et comment, et poser toutes ses questions d'un coup ; puis rendre la main. C'est le seul arrêt prévu.
2. **L'exécution** : après les réponses, aller jusqu'au bout sans rendre la main. On ne travaille que pendant sa réponse : un plan annoncé suivi d'une main rendue, c'est un chantier arrêté.
3. **Les images** : tout dessin passe par le sous-agent pixel-artist, sur une planche dans `.art-preview/` (à côté de Xéros pour l'échelle), avec une notification macOS (`osascript -e 'display notification "<ce qui est prêt>" with title "Xéros"'`) et une ligne « DESSIN À VALIDER » avec le chemin. Rien n'est intégré sans l'accord écrit de Grégoire. En attendant, avancer sur ce qui n'en dépend pas ; arrivé à l'intégration sans accord, renotifier et rendre la main.

## Consignes

- Ne jamais éditer `src/generated/` ni `tiled/tilesets/` : modifier `art/` ou `src/content/`, puis `npm run art`.
- Nouvel objet : sa fiche dans docs/objets/ d'abord (modèle dans `docs/objets/README.md` : identité, masse, dimensions, toutes ses vues, regroupement, gestes, travail, arme, origine, devenir, vérification).
- Nouvel objet : ses vues de tous les côtés, selon sa symétrie, dès sa création (`views` dans props.json ou items.json : `round` une vue, `symmetric` deux, `<image>-ns`, `four` quatre, `<image>-r1` à `-r3` ; `lying` pour ce qui est couché : le nord-sud a les dimensions de l'est-ouest inversées, règle D de `docs/STYLE.md` section 8). `validate.ts` le vérifie ; un objet ancien sans toutes ses vues va dans `VIEWS_TODO` (validate.ts), avec sa raison, et `npm run check` affiche ce qui reste.
- Ajouter du contenu (propriétés de tuile, objet, personnage, dialogue) = éditer `src/content/` (une tuile se dessine d'abord dans `art/`) ; ne pas coder de contenu en dur dans les scènes.
- Une carte = un fichier Tiled `tiled/maps/<id>.tmj`, traduit par `npm run maps` (le jeu ne lit jamais Tiled). Règles de pose (calque `ground`, types `Spawn`, `Exit`, `Npc`, objets) dans le README.
- Nouvelle carte : esquisse (`tiled/sketches/<id>.json`, lettres), `npm run sketch -- <id>`, puis retouches dans Tiled. Une carte existante ne se refait jamais depuis l'esquisse : le `.tmj` fait foi. Nouvelle lettre = `tiled/sketch-legend.json`.
- Les numéros de tuiles vivent dans `art/tile-registry.json` (committé) : `npm run art` ajoute les nouvelles tuiles en fin de liste ; ne jamais réordonner ni supprimer une entrée, car les .tmj stockent ces numéros.
- Nouvel objet posable : une entrée de `src/content/props.json` ; sa clé (anglais, kebab-case, reprend la clé d'image) est le type de l'objet dans Tiled, `name` est le nom affiché en français, `dims` ses dimensions réelles en centimètres (forme, sens). Sa taille à l'écran en découle par le gabarit (`docs/STYLE.md` section 8, `src/content/gabarit.ts`), vérifiée à 2 px près par `validate.ts` ; `EXCEPTIONS` n'accueille que les objets anciens et les écarts voulus par Grégoire, avec leur raison (le têtard : tête stylisée).
- Trois arbres, deux sortes : `big-…` (tronc de 55 cm : le gros grand `big-tree` et le têtard `big-pollard`, qui partagent souche, diamètre de bois et tas) et `normal-…` (tronc de 30 cm, 7 m), nom `<sorte>-<pièce>` (`big-tree`, `big-pollard`, `normal-felled-tree`, leurs tas se calculent). Abattu, un arbre est couché d'un seul tenant (`<arbre>-felled-tree`) ; ébranché, son tronc devient une seule pièce de bois de sa longueur utile (`harvest` : `becomes: "wood-piece"`, `wood` : diamètre et longueur, sur la grille). **Un nouvel arbre = des données et des dessins, jamais de code** : dans `props.json`, l'arbre debout (`harvest` : `work.fell`, `stages`, `fall` réduit à `image`, `anim`, `left.image`, `becomes` sa souche, `spawns` son arbre couché par son seul `type` ; et sa géométrie `tree`, `TreeSchema` de types.ts : pied, ombre, coupe, plancher, entaille, trait, fente, penche, copeaux, éclats, et `fall` : ce qui tombe, `body` ou `bark`, houppier couché, aplatissement, bout scié, ombres à 10° et 45°, `crop`), sa souche, son arbre couché (`work.limbs`, `stages`, `becomes: "wood-piece"`, `wood`) ; ses dessins, enregistrés par clé d'image (`registerTree`, art/world/tree-registry.ts : l'arbre debout `body`, sa souche et son pied, son arbre couché tiré de son houppier couché `lying`, son tronc nu pour une chute `bark`, sa matière dans wood.ts ; un nouveau fichier de dessin s'importe en tête de art/world/trees.ts) ; sa fiche. Tout le reste se tire de là, pour tous les arbres de `props.json` qui ont `harvest.fall` (art/world/trees.ts) : ses étapes d'abattage des deux côtés (felling.ts), ses deux chutes (la chute commune à toutes les sortes, tree-fall.ts), son arbre couché et son ébranchage (work-stages.ts). Ses décalages (`fall.x`, `fall.foot`, `fall.left.x`, `at`, la place de ce qui naît, `at` de l'arbre couché) sont calculés par `npm run art` (tools/build-trees.ts, `src/generated/trees.json`, joints à props.json par `withTreeLayout` de src/content/treeLayout.ts) : jamais écrits dans props.json, qui les refuse. Une nouvelle sorte, en plus : son contrat de géométrie `<sorte>-geometry.ts`, son diamètre de bois dans `wood.json` s'il est nouveau. Le renommage d'une clé change le format de GameState : augmenter `SAVE_VERSION`. Vérifier avec `npm run test:fast` (tools/test-arbres.ts : chaque arbre, chaque côté, étapes, chute sans saut, décalages, ébranchage, pièce de bois) et `npm run art:preview` : `.art-preview/arbres.png` (les arbres à chaque étape).
- Masses et force : tout objet qu'on prend, pose ou roule a une `mass` (items.json, props.json ; bois en `"wood"`, calculée par `src/content/mass.ts`), sinon `validate.ts` refuse. Les seuils de Xéros sont dans `src/content/strength.json` (composant `entities/Strength.ts`), jamais en dur ; ?dieu « force » les multiplie : le multiplicateur plafonne au plus fort des humains (`human` de Strength.ts, `swing.humanMax` sur le couple de Xéros), le même pour frapper, porter, marcher chargé et rouler (`swinger`, `carry`, `walk`, `roll` ; la force surhumaine lèvera tous les plafonds, plus tard). Ce qui roule : la pièce de bois ronde (son `roll` se tire de ses réglages, 4 images de roulement par partie dans sa planche), mécanique dans `src/systems/roll.ts`, constantes `ROLL` de config.ts. La fiche d'objet a une rubrique « Masse ».
- Tout dessin (nouveau sprite ou retouche dans `art/`) passe par le sous-agent `pixel-artist` (`.claude/agents/pixel-artist.md`, sur Opus), qui applique `docs/STYLE.md`.
- Nouveau sprite : l'ajouter dans `art/`, le déclarer dans `art/index.ts`, vérifier l'aperçu avec `npm run art:preview` (images dans `.art-preview/`, à regarder).
- Nouvelle capacité de personnage : un composant attaché à `Actor`, pas une sous-classe.
- Nouveau personnage parlant : une entrée de `src/content/characters.json` (clé = clé du sprite ; portrait 64 px seulement, `portrait-<nom>-64`), puis, pour le poser sur une carte, un point Tiled de type `Npc` (`character`, `dialogue`, `facing`) ; ne pas coder de PNJ dans les scènes.
- Nouveau champ de contenu : le déclarer dans `src/content/types.ts` (schéma Zod) ; nouveau lien entre fichiers : le vérifier dans `src/content/validate.ts`.
- Nouvelle mécanique du monde : un fichier dans `src/systems/`, appelé depuis `WorldScene.update` selon le mode. Un travail qui se fait en longeant une pièce (la doloire ; plus tard le rabot, la scie de long) passe par le rail de `src/systems/rail.ts` (mode `rail` de WorldScene), pas par un déplacement à part ; **un travail est au coup** (CONCEPTION « Le travail ») : une quantité de matière (`world/workPlan.ts` : `harvest.work` de props.json, le diamètre des pièces de bois), chaque coup en enlève une part selon son énergie (`world/swing.ts`, la physique du combat : la force de strength.json `swing`, l'outil `work` d'items.json, les coups de `work.json`), la durée découle des coups et des pauses de souffle, jamais imposée ; chaque coup se paie au joule (`breathPerJ`, `ceilingPerJ` de `work` de stamina.json, `strokeCost` de workPlan.ts), jamais d'un prix fixe ; la force du coup plafonne à `humanMax` (strength.json) ; un clic court de la main de l'outil lance tout le travail, Xéros frappe seul jusqu'au résultat avec ses pauses de souffle, un pas ou Échap arrête après le coup en cours ; la force (?dieu) agit au coup suivant ; ?debug montre au-dessus de Xéros la force, l'énergie et la part par coup ; la vitesse de simulation de ?dieu (x1 à x50, `systems/simSpeed.ts` : plusieurs pas de jeu de taille normale par image) ; `src/systems/work.ts` (mode `work`) et le rail ; jauge `entities/WorkBar.ts` ; part enlevée dans `work` de GameState ; ?dieu « Finir le travail » ; les durées des images d'un geste de travail viennent de ses `phases` (gestures.json) ; deux points de calage seulement (`calibration` de work.json, vérifiés par validate.ts ; `npm run check` affiche la durée de chaque travail) ; jamais de saut d'horloge pour un travail ; la vitesse du temps du joueur (V seul, en boucle : x1, x2, x5, x10, x20, puis x1 ; `speeds` de time.json ; aucune touche pour revenir en arrière) est la vitesse de simulation (`systems/simSpeed.ts`), une attaque ramène à x1, x50 réservé à ?dieu ; la lumière suit l'heure (`daylight` de world.json, `world/daylight.ts`, `systems/daylight.ts` : un voile à la profondeur des pénombres, les rais `sunpatch` selon le soleil, les lueurs par-dessus) ; les vitesses de déplacement n'ont qu'une source (`PLAYER.walk`, `PLAYER.run` en m/s, `systems/speeds.ts`, réglables dans ?dieu) : chargé, fatigué, la bille poussée en dérivent (une part de la marche), jamais une vitesse à part ; la face entamée d'une pièce de bois : `dressed` (CONCEPTION « L'équarrissage par passes »). Événements entre scènes : constantes de `src/events.ts`.
- Ce qui change pendant la partie (les deux mains, objet récolté, objet pris ou posé, objet au sol) vit dans `GameState` (`src/state/`), rangé par carte et par identifiant d'objet Tiled ; ne pas le garder dans une scène ni dans le registry de Phaser.
- Nouvel objet possédable : une entrée de `src/content/items.json` (icône `item-<clé>`, `hands` : 2 s'il est lourd ou long). Pas de barre ni de besace : l'inventaire, ce sont les deux mains de `GameState` (`hands`, `both`), changées par `take`, `release` ; pas de main active : chaque clic dit sa main (clic gauche, la droite ; clic droit, la gauche).
- Nouvel objet du monde qu'on prend : un composant `take` dans `props.json` (`hands`, `icon`, `hold`), pas de code. Prendre, poser, lâcher : `src/systems/hands.ts`.
- Poser : un seul chemin pour tout ce qu'on porte (`dropTarget`, `put`, `ghostOf` de `src/systems/hands.ts`) : le clic court de la main qui tient l'objet ou A (Q en QWERTY), au fantôme qui suit le curseur et montre où et dans quel sens (R) ; à la place libre la plus proche à côté si devant est pris (`PUT_DOWN` de config.ts) ; jamais de pose à part pour un objet.
- Tas : un tas naît d'une pièce posée contre une pièce identique seule au sol, ou grandit sur un tas commencé ; il prend tout de sa première pièce et n'accepte que des pièces identiques. **Les tas de bois se calculent** d'après la section de leur pièce (`src/world/woodPile.ts` : pyramide pour le rond, rangées de 3 × 3 pour la demi-bille, la poutre, le quartier en triangles, pointe en l'air puis en bas, `point`), pour toute longueur ; affichage couche par couche, de l'arrière vers l'avant ; seul ce qui se porte (`carry` de strength.json) va en tas. `src/content/piles.json` ne garde que ce qui ne se calcule pas (branches, fagots, liens) : un genre = une entrée (`piece`, `start`, `blockFrom`, `places` : `layer`, `on`, `image`, `x`, `y`, `body` au sol), une image par place dessinée par le pixel-artist dans `art/world/piles.ts`. GameState : un tas entrepose `pile` (genre écrit) ou `wood` (la pièce) ; `pileDefOf(kindOf(tas))` et `shapeOf` (`src/world/pileShape.ts`) donnent sa forme dans son sens. Tout se vérifie à l'œil sur `.art-preview/piles.png` (`npm run art:preview` : les genres écrits, puis des tas de bois de plusieurs longueurs et états).
- Quantité mesurée (le rouleau de corde) : `length` dans props.json (`start`, `cut`, `piece`, en cm), longueur gardée par GameState (`length` de ce qu'on tient, d'un objet né ou changé), affichée dans la case de main (HudScene). Poser un objet sur un autre : `rest` du support et `bears` de ce qu'il devient ; la coupe à l'outil passe par son `harvest` (`cutBorne`, `src/systems/harvest.ts`).
- Lien d'un tas : `tie` du genre dans piles.json (`item`, `north` et `south` : ses deux bouts sous le tas, accrochés aux pièces au sol par `tieImages` de `pileShape.ts` ; `alone` seul par terre ; `into`), `tie` du tas dans GameState (un tas lié peut être vide). Nouer, dénouer (clic maintenu, main vide) : `src/systems/knot.ts` (un fagot se noue dès 2 branches ; son nombre, `bundle` du tas et du fagot tenu, fait son image `<image>-n<n>`, sa masse, et le tas qui l'accepte : `bundleOfKind`, `pileDefOf` de pileShape.ts) ; clic court ou maintenu et sa jauge : `src/systems/longPress.ts` (un seul seuil, `LONG_PRESS` ; le clic court agit au relâchement ; ce que fait chaque clic : `clickPlan` de `src/world/clickAction.ts`). Nombre de pièces d'un tas : `count` du genre, `src/systems/pileCount.ts`.
- Tout objet tenu se voit sur Xéros (composant `Hold`) : son `hold` (`stance` : `hand`, `shoulder` ou `carry` ; `image` : planche `held-<…>` de `art/items/carried.ts`, vues `down`, `up`, `right`, dessinée par le pixel-artist) ; les points d'accroche par posture et par image sont dans `src/content/hold.json`, tirés des constantes `HAND_POINTS`, `SHOULDER_POINTS`, `CARRY_HANDS` de `art/characters/xeros.ts`. Nouvelle posture = ses animations `<posture>-idle/walk-*` et son entrée dans `hold.json`. **Un objet à plusieurs états (nombre, taille, âge…) suit son état dans toutes ses vues, au sol comme en main** (règle de Grégoire) : le fagot et son nombre de branches, de 2 au tas plein, ont chacun leur vue au sol et en tas (`<image>-n<n>`, `-ns`), leur planche portée (`held-faggot-n<n>`) et leur icône (`item-faggot-n<n>`), choisies par un seul chemin (`stateImage` de `src/world/pileShape.ts` : le sol, le fantôme, la main, la case de main ; le dessin de base n'est que celui du catalogue) ; `validateStates` (validate.ts) le vérifie, `tools/test-fagot.ts` aussi.
- Endurance en trois niveaux (CONCEPTION « Le temps ») : souffle, plafond du jour, maximum ; valeurs et prix de chaque effort dans `src/content/stamina.json` (jamais en dur ; `breath` : ce que coûte et rend le souffle), composant `entities/Stamina.ts` attaché à `Player`, mécanique dans `src/systems/effort.ts` ; **le travail au coup se paie au joule** (`breathPerJ`, `ceilingPerJ` de `work`, CONCEPTION « Le travail ») ; `costs` ne vaut que pour les gestes sans matière (planter le coin ou un piquet, nouer, pivoter, dresser, porter, courir, couper un lien sur le billot) ; le rocher (la pioche, `break` de `harvest.work`) et l'attaque se paient au joule comme le reste : un nouveau geste sans matière qui coûte = une clé de `costs`, un `afford` (ou `allows` avant, `spend` après) ou un `drain` (avec son souffle par seconde) à l'endroit où il se fait. À bout de souffle, l'effort attend sans message (Xéros souffle, `entities/Breath.ts`, la barre clignote) ; plafond à zéro, il est refusé (message « Xéros est épuisé. Il faut dormir. »). Barre du HUD : `art/ui/stamina-bar.ts` (contrat de pose), `STAMINA_BAR` de config.ts. `stamina` (les trois niveaux, et `woke`, le plafond au réveil) et `clock` vivent dans GameState (`setStamina`, `sleep`, `advanceClock`) ; le sommeil (lever, ce que rend la nuit, veille de nuit) : `world/sleep.ts`, `sleep` de stamina.json ; test `tools/test-sleep.ts`. Dormir : `pallet-sleep` (dialogue à `choices`, `action: sleep`). Pivoter une pièce de bois : `turn` de sa définition (seul son sens change), `systems/turnLog.ts`, clic maintenu, les deux mains libres.
- Touches du joueur : lues par leur place (`KeyboardEvent.code`, `src/input/PlayerInput.ts`), jamais par leur lettre : ZQSD en AZERTY = WASD en QWERTY ; lâcher (Q en QWERTY) est le A d'un AZERTY ; tourner ce qu'on tient, R (même place) ; la souris vise, clic gauche = main droite, clic droit = main gauche (`docs/COMMANDES.md`). **Un appui n'est jamais perdu** (règle de Grégoire : un joueur sur une machine lente ne voit jamais ses appuis ignorés) : appuis et relâchements sont écoutés sur la fenêtre, à l'instant de l'événement (`src/input/keyLatch.ts`) ; un appui plus court qu'une image est gardé jusqu'à ce que le jeu le lise, une flèche tapée déplace d'une image, et la durée d'un appui maintenu est sa durée vraie, jamais le temps mis à la lire (`pressEnd` : une image longue ne fait pas d'un appui court un appui long) ; les clics du mode construction vont en file (`clicks` de `systems/build.ts`). Test : `tools/test-input.ts` (test:fast), et `npm run test:noeud` sur une machine lente simulée.
- Nouvelle récolte : un composant `harvest` dans `props.json`, pas de code (ce qui naît d'une récolte : `spawns` ; le geste : `gesture` ; ce qu'elle retire sans le rendre : `waste`, nommé, et le bilan des masses de `harvestBalance` de validate.ts : un arbre et ce qui en sort ont une masse, abattre ne retire que les copeaux de l'entaille, `fellVolume`). Une récolte qui se travaille (avec un outil) est **au coup** : sa matière dans `harvest.work` (`fell` : le diamètre du tronc ; `limbs` : le nombre et le diamètre des branches ; `whittle` : la pointe ; `harvestJob` de `src/world/workPlan.ts`), ses étapes logiques dans `hits` (l'objet tremble à chacune), ses images d'étape dans `stages` (la part de matière enlevée, de 0 à 1, croissante, à laquelle l'objet prend `<image>-stage-<n>` ; pour un arbre qui tombe, aussi `<image>-left-stage-<n>`, l'entaille dessinée du côté gauche, sans retournement), dessinées par le pixel-artist (`art/world/work-stages.ts`) ; sans `work`, la récolte reste à l'ancienne (un coup par appui, prix fixe de `costs` : à réserver aux gestes sans matière). Un arbre qui tombe (`fall`) tombe du côté où Xéros frappe : il s'y place lui-même au lancement, le côté est gardé avec le travail (`side` de `work` dans GameState).
- Nouveau geste : une entrée de `src/content/gestures.json`, les animations `<geste>-<direction>` du corps dans `art/characters/xeros.ts` et le geste ajouté à `heldToolSheet` (`art/items/held.ts`) ; le jeu choisit les images d'outil par nom d'animation, jamais par indice.
- Nouvel outil en main, à l'échelle (5 cm par pixel, prise au centre d'images de TOOL_SIZE = 48 px) : cinq dessins en zones de matière et leur table `materials`, déclarés dans `art/items/held.ts` (convention dans l'en-tête de `art/lib/held.ts`). Règle : coup horizontal (`use`), on voit la face de l'outil, de profil (`diag`, `upright`, référence `docs/references/hache-vue-de-cote.png`) ; coup vertical (`chop`), on le voit par la tranche (`flat`, `flatDiag`, `flatEnd`, référence `docs/references/hache-vue-de-dessus.png`). La planche `tool-<objet>` en est tirée pour toutes les poses de `src/content/gestures.json` (champ `base` : le dessin de chaque pose), puis éclairée en haut à gauche par `art/lib/light.ts` ; ne pas toucher aux gestes du corps. Ses données de coup : `work` de l'outil dans items.json (`length`, `grip`, `balance`, `edge`, `aim` ; sa masse est `mass`), le coup qu'il donne dans `strokes` de `src/content/work.json` (le geste, l'angle, les temps hors frappe), les `phases` de son geste dans gestures.json (la durée de chaque image) ; `world/swing.ts` en tire l'énergie et la durée de chaque coup.
- Bâtiment : un jeu de pièces (un objet de `props.json` par pièce, chacune avec sa fiche et ses `dims`) et **un plan** dans `src/content/plans.json` (en cm : emprise, coins, `stake` qui trace, étapes dans l'ordre réel, chaque place avec sa `piece`, `at`, `orientation`, `on`, `corner`, `accepts`) : **un nouveau bâtiment = un plan dans `plans.json`**, sans code nouveau ; une étape non encore jouable porte `soon: true` ; une place qui demande une poutre : `accepts.wood` (`section`, `length` exacte ; `world/places.ts` dit le refus), et **toute place dont la poutre dépasse la force de Xéros accepte l'aide de la mère** (clic maintenu, main vide, fondu : `help`, `skipStep` de `systems/site.ts` ; `pieces` du chantier garde la pièce d'origine). `npm run art:preview` montre le bâtiment monter (`<bâtiment>-<n>.png`). Tracer et bâtir en jeu : `systems/site.ts`, état dans `sites` de GameState (`startSite`, `plantSiteStake`, `pullSiteStake`, `placeSitePiece`) ; une planchette qui enseigne un plan : `teaches` dans `props.json`. Les places d'un tas et d'un chantier sont le moteur commun `world/places.ts` (une place accepte un genre, ou une pièce précise avec son message de refus). Pièce en hauteur : rangées vides sous elle dans son image, le bas de l'image au sol à son bord sud ; pièce qui relie des appuis au sol : `ground: true` dans `dims` (gabarit H + D) ; seules les pièces à `body` bloquent ; pièce de toit : `roof: true` (dehors, le toit d'un bâtiment où l'on entre ne s'efface jamais, celui d'un abri ouvert quand Xéros est dessous ; devant une fenêtre au volet ouvert, le toit s'ouvre au-dessus de cette pièce seule ; la lueur d'un feu sous un toit opaque est cachée, lumière comprise : `lightCovers`, `glowAt` de GameMap ; `src/world/roofView.ts`, `src/systems/roofs.ts`, `ROOF` de config.ts ; test `tools/test-roofs.ts`) ; la couverture porte `shadow` (hauteurs sud et nord, en cm) : son ombre portée est calculée par le jeu (`src/world/roofShadow.ts`, `SHADOW` de config.ts), jamais peinte. Bois des bâtiments : la rampe du bois travaillé à son âge (`woodAges`, ci-dessous). **Un chantier montre les vraies pièces posées** : une place qui demande une poutre (`accepts.wood`) a pour `piece` `wood-piece` et `orientation` `upright`, et la pièce dressée est la pièce de bois debout (`axis: 'up'`, `up` des aspects du normal dans `wood.json`, planche `wood-normal-up`, `uprightOf`, `lay` de `site.ts`), jamais un dessin propre au bâtiment ; le fantôme de la place est cette même image en transparence ; une étape `soon` garde ses dessins en fantôme et sa `note` dit ce qu'elle sera. Ne pas coder un bâtiment dans une scène.
- Sauvegarde (`src/state/save.ts`, `src/systems/autosave.ts`) : GameState s'écrit tout seul à chaque changement, parce que chaque fonction de `GameState.ts` avance le compteur `revision` ; une nouvelle fonction qui modifie GameState doit l'avancer aussi. Nouveau champ de GameState ou format changé d'une façon que l'ancien ne lit plus : augmenter `SAVE_VERSION`. Une sauvegarde qui nomme un contenu (carte, objet, tas) est contrôlée par `missingContent` (save.ts) : nouveau lien = l'y ajouter. Avant une fusion dans main (règle de Grégoire) : un chantier qui ne touche pas au moteur se fusionne après `npm run build` et les scénarios qu'il touche (`npm run test:<nom>`, lancés seuls), puis la suite complète tourne en arrière-plan (`npm run test:scenarios:bg:all`) ; un échec donne aussitôt un commit de correction. - **Le monde ne limite jamais, seul le personnage limite** (règle de base de Grégoire, CONCEPTION « Le monde ne limite pas ») : une action est toujours possible en soi ; ce qui l'empêche, ce sont les caractéristiques de Xéros (force, endurance, compétences : `Strength`, `Stamina`), jamais une règle écrite pour un objet, une taille, une longueur ou une masse. S'il peut soulever, il peut empiler ; s'il a la force, il peut tout faire. Un refus le dit par ce qui lui manque (« Trop lourde pour lui (107 kg, il en porte 70) »), jamais « impossible ». Une limite qui ne vient que d'un dessin manquant se liste avec sa raison (CONCEPTION) et se lève avec le pixel-artist. `npm run test:contrats` le vérifie (à la force maximale, tout ce qui se soulève se prend et s'empile ; à la sienne, le refus dit « pour lui »). **La matière se conserve** : nouer, dénouer, empiler, reprendre d'un tas, fendre, couper, transformer ne créent jamais de matière (masse totale et nombre de pièces égaux avant et après), sauf ce qu'un travail retire et nomme (`waste` d'une transformation de transforms.json, ou d'une fente : `split` de wood.json) ; `validate.ts` refuse une perte sans nom ; `tools/test-matiere.ts` (test:fast) et `npm run test:noeud` (le fagot noué, posé seul, rechargé, dénoué) le vérifient.
- **Ne jamais supprimer un fichier ou un dossier qui n'est pas suivi par git** (règle de Grégoire), sauf ce qu'un outil du dépôt reconstruit (`src/generated/`, `.art-preview/`, `node_modules/`) : le déplacer dans `.poubelle/` à la racine du dépôt (ignorée par git), en gardant son chemin d'origine (`.poubelle/<chemin>`), et le dire dans le récapitulatif du chantier. La poubelle concerne ce qu'un humain ou un agent a écrit, pas les fichiers temporaires qu'un outil du dépôt crée puis efface lui-même (le cache de Vite de `tools/lib/playtest.ts`, les plans `essai-*` de `tools/run-scenarios.ts`, la copie figée de `tools/scenarios-bg.ts`).
