# Xéros — consignes pour les agents de code

Lis `README.md` (architecture et quatre règles) avant toute modification, et `docs/CONCEPTION.md` (univers, personnages, lieux, feuille de route) avant tout travail sur le contenu.

- Ne jamais éditer `src/generated/` ni `tiled/tilesets/` : modifier `art/` ou `src/content/`, puis `npm run art`.
- Nouvel objet : sa fiche dans docs/objets/ d'abord (modèle dans `docs/objets/README.md` : identité, dimensions, toutes ses vues, regroupement, gestes, origine, devenir, vérification).
- Nouvel objet : ses vues de tous les côtés, selon sa symétrie, dès sa création (`views` dans props.json ou items.json : `round` une vue, `symmetric` deux, `<image>-ns`, `four` quatre, `<image>-r1` à `-r3` ; `lying` pour ce qui est couché : le nord-sud a les dimensions de l'est-ouest inversées, règle D de `docs/STYLE.md` section 8). `validate.ts` le vérifie ; un objet ancien sans toutes ses vues va dans `VIEWS_TODO` (validate.ts), avec sa raison, et `npm run check` affiche ce qui reste.
- Ajouter du contenu (propriétés de tuile, objet, personnage, dialogue) = éditer `src/content/` (une tuile se dessine d'abord dans `art/`) ; ne pas coder de contenu en dur dans les scènes.
- Une carte = un fichier Tiled `tiled/maps/<id>.tmj`, traduit par `npm run maps` (le jeu ne lit jamais Tiled). Règles de pose (calque `ground`, types `Spawn`, `Exit`, `Npc`, objets) dans le README.
- Nouvelle carte : esquisse (`tiled/sketches/<id>.json`, lettres), `npm run sketch -- <id>`, puis retouches dans Tiled. Une carte existante ne se refait jamais depuis l'esquisse : le `.tmj` fait foi. Nouvelle lettre = `tiled/sketch-legend.json`.
- Les numéros de tuiles vivent dans `art/tile-registry.json` (committé) : `npm run art` ajoute les nouvelles tuiles en fin de liste ; ne jamais réordonner ni supprimer une entrée, car les .tmj stockent ces numéros.
- Nouvel objet posable : une entrée de `src/content/props.json` ; sa clé (anglais, kebab-case, reprend la clé d'image) est le type de l'objet dans Tiled, `name` est le nom affiché en français, `dims` ses dimensions réelles en centimètres (forme, sens). Sa taille à l'écran en découle par le gabarit (`docs/STYLE.md` section 8, `src/content/gabarit.ts`), vérifiée à 2 px près par `validate.ts` ; `EXCEPTIONS` n'accueille que les objets anciens et les écarts voulus par Grégoire, avec leur raison (le têtard : tête stylisée).
- Trois arbres, deux sortes : `big-…` (tronc de 55 cm : le gros grand `big-tree` et le têtard `big-pollard`, qui partagent souche, diamètre de bois et tas) et `normal-…` (tronc de 30 cm, 7 m), nom `<sorte>-<pièce>` (`big-tree`, `big-pollard`, `normal-felled-tree`, leurs tas se calculent). Abattu, un arbre est couché d'un seul tenant (`<arbre>-felled-tree`) ; ébranché, son tronc devient une seule pièce de bois de sa longueur utile (`harvest` : `becomes: "wood-piece"`, `wood` : diamètre et longueur, sur la grille). Une variante d'une sorte (comme le têtard) = son arbre debout, ses chutes (la chute commune des gros : `Faller` de big-felled.ts) et son arbre couché, une entrée de `props.json`, une fiche ; et une ligne de `KINDS` (tools/lib/trees-preview.ts). Une nouvelle sorte d'arbre = ses dessins (`art/world/<sorte>-*.ts`, matière de `wood.ts`, contrat de géométrie dans un fichier `<sorte>-geometry.ts`), ses entrées de `props.json`, son diamètre de bois dans `wood.json` s'il est nouveau, sa fiche, et c'est tout : le moteur n'a rien de propre à une sorte. Le renommage d'une clé change le format de GameState : augmenter `SAVE_VERSION`. Vérifier avec `npm run art:preview` : `.art-preview/arbres.png` (les trois arbres à chaque étape).
- Masses et force : tout objet qu'on prend, pose ou roule a une `mass` (items.json, props.json ; bois en `"wood"`, calculée par `src/content/mass.ts`), sinon `validate.ts` refuse. Les seuils de Xéros sont dans `src/content/strength.json` (composant `entities/Strength.ts`), jamais en dur. Ce qui roule : la pièce de bois ronde (son `roll` se tire de ses réglages, 4 images de roulement par partie dans sa planche), mécanique dans `src/systems/roll.ts`, constantes `ROLL` de config.ts. La fiche d'objet a une rubrique « Masse ».
- Tout dessin (nouveau sprite ou retouche dans `art/`) passe par le sous-agent `pixel-artist` (`.claude/agents/pixel-artist.md`, sur Opus), qui applique `docs/STYLE.md`.
- Nouveau sprite : l'ajouter dans `art/`, le déclarer dans `art/index.ts`, vérifier l'aperçu avec `npm run art:preview` (images dans `.art-preview/`, à regarder).
- Nouvelle capacité de personnage : un composant attaché à `Actor`, pas une sous-classe.
- Nouveau personnage parlant : une entrée de `src/content/characters.json` (clé = clé du sprite ; portrait 64 px seulement, `portrait-<nom>-64`), puis, pour le poser sur une carte, un point Tiled de type `Npc` (`character`, `dialogue`, `facing`) ; ne pas coder de PNJ dans les scènes.
- Nouveau champ de contenu : le déclarer dans `src/content/types.ts` (schéma Zod) ; nouveau lien entre fichiers : le vérifier dans `src/content/validate.ts`.
- Nouvelle mécanique du monde : un fichier dans `src/systems/`, appelé depuis `WorldScene.update` selon le mode. Un travail qui se fait en longeant une pièce (la doloire ; plus tard le rabot, la scie de long) passe par le rail de `src/systems/rail.ts` (mode `rail` de WorldScene, Échap ou un pas l'arrête ; la passe dure son temps réaliste), pas par un déplacement à part ; tout autre travail qui dure (abattre, récolter, couper, fendre, tailler) passe par `src/systems/work.ts` (mode `work` : Xéros répète son geste pendant les `minutes` des données, en temps réel, étapes `hits` réparties, jauge `entities/WorkBar.ts`, endurance au fil des coups, part faite dans `work` de GameState, ?dieu « Finir le travail ») ; jamais de saut d'horloge pour un travail ; la vitesse du temps est en pause à x1 (`accelerate` de time.json) ; la face entamée d'une pièce de bois : `dressed` (CONCEPTION « L'équarrissage par passes »). Événements entre scènes : constantes de `src/events.ts`.
- Ce qui change pendant la partie (les deux mains, objet récolté, objet pris ou posé, objet au sol) vit dans `GameState` (`src/state/`), rangé par carte et par identifiant d'objet Tiled ; ne pas le garder dans une scène ni dans le registry de Phaser.
- Nouvel objet possédable : une entrée de `src/content/items.json` (icône `item-<clé>`, `hands` : 2 s'il est lourd ou long). Pas de barre ni de besace : l'inventaire, ce sont les deux mains de `GameState` (`hands`, `both`, `active`), changées par `take`, `release`, `switchHand`.
- Nouvel objet du monde qu'on prend : un composant `take` dans `props.json` (`hands`, `icon`, `hold`), pas de code. Prendre, poser, lâcher : `src/systems/hands.ts`.
- Poser : un seul chemin pour tout ce qu'on porte (`dropTarget`, `put`, `ghostOf` de `src/systems/hands.ts`) : E dans le vide ou Q, avec un fantôme qui montre où et dans quel sens (R) ; à la place libre la plus proche à côté si devant est pris (`PUT_DOWN` de config.ts) ; jamais de pose à part pour un objet. Main active qui se vide : elle passe sur l'autre main si elle tient un objet (`followHeld`, GameState).
- Tas : un tas naît d'une pièce posée contre une pièce identique seule au sol, ou grandit sur un tas commencé ; il prend tout de sa première pièce et n'accepte que des pièces identiques. **Les tas de bois se calculent** d'après la section de leur pièce (`src/world/woodPile.ts` : pyramide pour le rond, rangées de 3 × 3 pour la demi-bille, la poutre, le quartier en triangles, pointe en l'air puis en bas, `point`), pour toute longueur ; affichage couche par couche, de l'arrière vers l'avant ; seul ce qui se porte (`carry` de strength.json) va en tas. `src/content/piles.json` ne garde que ce qui ne se calcule pas (branches, fagots, liens) : un genre = une entrée (`piece`, `start`, `blockFrom`, `places` : `layer`, `on`, `image`, `x`, `y`, `body` au sol), une image par place dessinée par le pixel-artist dans `art/world/piles.ts`. GameState : un tas entrepose `pile` (genre écrit) ou `wood` (la pièce) ; `pileDefOf(kindOf(tas))` et `shapeOf` (`src/world/pileShape.ts`) donnent sa forme dans son sens. Tout se vérifie à l'œil sur `.art-preview/piles.png` (`npm run art:preview` : les genres écrits, puis des tas de bois de plusieurs longueurs et états).
- Quantité mesurée (le rouleau de corde) : `length` dans props.json (`start`, `cut`, `piece`, en cm), longueur gardée par GameState (`length` de ce qu'on tient, d'un objet né ou changé), affichée dans la case de main (HudScene). Poser un objet sur un autre : `rest` du support et `bears` de ce qu'il devient ; la coupe à l'outil passe par son `harvest` (`cutBorne`, `src/systems/harvest.ts`).
- Lien d'un tas : `tie` du genre dans piles.json (`item`, `north` et `south` : ses deux bouts sous le tas, accrochés aux pièces au sol par `tieImages` de `pileShape.ts` ; `alone` seul par terre ; `into`), `tie` du tas dans GameState (un tas lié peut être vide). Nouer, dénouer (E maintenu) : `src/systems/knot.ts` ; E maintenu et sa jauge : `src/systems/longPress.ts` (une cible n'attend que si `KnotSystem.holds` la reconnaît ; E court garde son rôle). Nombre de pièces d'un tas : `count` du genre, `src/systems/pileCount.ts`.
- Tout objet tenu se voit sur Xéros (composant `Hold`) : son `hold` (`stance` : `hand`, `shoulder` ou `carry` ; `image` : planche `held-<…>` de `art/items/carried.ts`, vues `down`, `up`, `right`, dessinée par le pixel-artist) ; les points d'accroche par posture et par image sont dans `src/content/hold.json`, tirés des constantes `HAND_POINTS`, `SHOULDER_POINTS`, `CARRY_HANDS` de `art/characters/xeros.ts`. Nouvelle posture = ses animations `<posture>-idle/walk-*` et son entrée dans `hold.json`.
- Endurance en trois niveaux (CONCEPTION « Le temps ») : souffle, plafond du jour, maximum ; valeurs et prix de chaque effort dans `src/content/stamina.json` (jamais en dur ; `breath` : ce que coûte et rend le souffle), composant `entities/Stamina.ts` attaché à `Player`, mécanique dans `src/systems/effort.ts` ; un nouvel effort qui coûte = une clé de `costs`, un `afford` (ou `allows` avant, `spend` après) ou un `drain` (avec son souffle par seconde) à l'endroit où il se fait. À bout de souffle, l'effort attend sans message (Xéros souffle, `entities/Breath.ts`, la barre clignote) ; plafond à zéro, il est refusé (message « Xéros est épuisé. Il faut dormir. »). Barre du HUD : `art/ui/stamina-bar.ts` (contrat de pose), `STAMINA_BAR` de config.ts. `stamina` (les trois niveaux, et `woke`, le plafond au réveil) et `clock` vivent dans GameState (`setStamina`, `sleep`, `advanceClock`) ; le sommeil (lever, ce que rend la nuit, veille de nuit) : `world/sleep.ts`, `sleep` de stamina.json ; test `tools/test-sleep.ts`. Dormir : `pallet-sleep` (dialogue à `choices`, `action: sleep`). Pivoter une pièce de bois : `turn` de sa définition (seul son sens change), `systems/turnLog.ts`, R maintenu.
- Touches du joueur : lues par leur place (`KeyboardEvent.code`, `src/input/PlayerInput.ts`), jamais par leur lettre : ZQSD en AZERTY = WASD en QWERTY ; lâcher (Q en QWERTY) est le A d'un AZERTY ; tourner la bille, R (même place).
- Nouvelle récolte : un composant `harvest` dans `props.json`, pas de code (ce qui naît d'une récolte : `spawns` ; le geste : `gesture`).
- Nouveau geste : une entrée de `src/content/gestures.json`, les animations `<geste>-<direction>` du corps dans `art/characters/xeros.ts` et le geste ajouté à `heldToolSheet` (`art/items/held.ts`) ; le jeu choisit les images d'outil par nom d'animation, jamais par indice.
- Nouvel outil en main, à l'échelle (5 cm par pixel, prise au centre d'images de TOOL_SIZE = 48 px) : cinq dessins en zones de matière et leur table `materials`, déclarés dans `art/items/held.ts` (convention dans l'en-tête de `art/lib/held.ts`). Règle : coup horizontal (`use`), on voit la face de l'outil, de profil (`diag`, `upright`, référence `docs/references/hache-vue-de-cote.png`) ; coup vertical (`chop`), on le voit par la tranche (`flat`, `flatDiag`, `flatEnd`, référence `docs/references/hache-vue-de-dessus.png`). La planche `tool-<objet>` en est tirée pour toutes les poses de `src/content/gestures.json` (champ `base` : le dessin de chaque pose), puis éclairée en haut à gauche par `art/lib/light.ts` ; ne pas toucher aux gestes du corps.
- Bâtiment : un jeu de pièces (un objet de `props.json` par pièce, chacune avec sa fiche et ses `dims`) et **un plan** dans `src/content/plans.json` (en cm : emprise, coins, `stake` qui trace, étapes dans l'ordre réel, chaque place avec sa `piece`, `at`, `orientation`, `on`, `corner`, `accepts`) : **un nouveau bâtiment = un plan dans `plans.json`**, sans code nouveau ; une étape non encore jouable porte `soon: true` ; une place qui demande une poutre : `accepts.wood` (`section`, `length` exacte ; `world/places.ts` dit le refus), et **toute place dont la poutre dépasse la force de Xéros accepte l'aide de la mère** (E maintenu, fondu : `help`, `skipStep` de `systems/site.ts` ; `pieces` du chantier garde la pièce d'origine). `npm run art:preview` montre le bâtiment monter (`<bâtiment>-<n>.png`). Tracer et bâtir en jeu : `systems/site.ts`, état dans `sites` de GameState (`startSite`, `plantSiteStake`, `pullSiteStake`, `placeSitePiece`) ; une planchette qui enseigne un plan : `teaches` dans `props.json`. Les places d'un tas et d'un chantier sont le moteur commun `world/places.ts` (une place accepte un genre, ou une pièce précise avec son message de refus). Pièce en hauteur : rangées vides sous elle dans son image, le bas de l'image au sol à son bord sud ; pièce qui relie des appuis au sol : `ground: true` dans `dims` (gabarit H + D) ; seules les pièces à `body` bloquent ; pièce de toit : `roof: true` (s'efface quand Xéros est dessous, `src/systems/roofs.ts`, `ROOF` de config.ts) ; la couverture porte `shadow` (hauteurs sud et nord, en cm) : son ombre portée est calculée par le jeu (`src/world/roofShadow.ts`, `SHADOW` de config.ts), jamais peinte. Bois des bâtiments : la rampe du bois travaillé à son âge (`woodAges`, ci-dessous). **Un chantier montre les vraies pièces posées** : une place qui demande une poutre (`accepts.wood`) a pour `piece` `wood-piece` et `orientation` `upright`, et la pièce dressée est la pièce de bois debout (`axis: 'up'`, `up` des aspects du normal dans `wood.json`, planche `wood-normal-up`, `uprightOf`, `lay` de `site.ts`), jamais un dessin propre au bâtiment ; le fantôme de la place est cette même image en transparence ; une étape `soon` garde ses dessins en fantôme et sa `note` dit ce qu'elle sera. Ne pas coder un bâtiment dans une scène.
- Sauvegarde (`src/state/save.ts`, `src/systems/autosave.ts`) : GameState s'écrit tout seul à chaque changement, parce que chaque fonction de `GameState.ts` avance le compteur `revision` ; une nouvelle fonction qui modifie GameState doit l'avancer aussi. Nouveau champ de GameState ou format changé d'une façon que l'ancien ne lit plus : augmenter `SAVE_VERSION`. Une sauvegarde qui nomme un contenu (carte, objet, tas) est contrôlée par `missingContent` (save.ts) : nouveau lien = l'y ajouter. Jamais de plantage à la lecture : un message clair et une partie neuve.
- Mode construction (`?construire`, touche B ; CONCEPTION « Le mode construction ») : modèle sans Phaser `src/world/build.ts`, mécanique `src/systems/build.ts`, catalogue `src/build/` (rien que le contenu existant), pièces posées dans `builds` de GameState ; plans du bac à sable dans `src/content/plans/<nom>.json` (écrits par le serveur Vite, vérifiés par validate.ts). Un élément composé calculé = `variants` dans props.json (tirages `<image>-s<k>`, toutes leurs vues). Un morceau de mur qui se raccorde = `wall` dans props.json : ses tronçons (`world/wallRuns.ts`) sont dessinés dans le jeu par `world/walls.ts` (code pur, pierres en données dans `src/generated/wallStones.ts`) ; tout dessin de mur passe par le pixel-artist. Ce qui s'ouvre et se ferme en jeu (E) : `swing` dans props.json (deux clés, ses deux états, `world/build.ts` `swung`), pas de code. Assemblages (CONCEPTION « Les assemblages ») : jonctions entre deux pièces de bois, `joints` de GameState, `world/joints.ts` (règles) et `world/jointView.ts` (dessin commun) ; un nouvel assemblage = un type de `JointTypeSchema`, sa règle dans `judge`, sa marque dessinée par le pixel-artist (`art/world/joints.ts`), sa fiche. Tout objet du contenu est au catalogue, rangé par famille, avec un nom et une vignette : `validate.ts` le vérifie (`CATALOG_EXCLUDED` : les exclusions, avec leur raison). Test : `npm run test:construction` ; aperçus `.art-preview/solin-rectangle.png`, `.art-preview/assemblages.png`. Un bâtiment est validé quand un scénario le bâtit dans le mode construction avec les seules pièces du catalogue et l'enregistre comme plan (`npm run test:cabane`, CONCEPTION « La cabane en rondins » ; `npm run test:grange`, `npm run test:etal`, CONCEPTION « Les bâtiments du village »).
- Intérieurs (CONCEPTION « Les intérieurs ») : on entre dans un bâtiment posé par sa porte (`swing.passage` de props.json) ou une ouverture sous un linteau ; son intérieur se calcule de ses pièces (`world/interior.ts` sans Phaser, `world/interiorMap.ts`, `world/interiorView.ts`, `systems/interiors.ts`), jamais dessiné à la main ; une face du dedans qui manque se dessine comme vue `-r2` de la pièce (pixel-artist). Les meubles posés dedans vont dans `builds` de la carte `interieur:<carte>:<x>,<y>` de GameState. Test : `npm run test:interieur`, aperçu `.art-preview/interieurs.png`.
- Le monde (CONCEPTION « Le monde ») : vingt zones de 125 × 125 cases (`tiled/maps/<zone>.tmj`), assemblées dans `tiled/maps/monde.world` (place de chaque zone, lue par build-maps : `world` de la carte) ; on passe d'une zone à la voisine en marchant hors du bord (`world/zones.ts` sans Phaser, `systems/zones.ts`, `crossTo` de WorldScene, sans fondu), la bande des voisines est dessinée au-delà du bord (`world/zoneBand.ts`, `ZONES` de config.ts). Une nouvelle zone = sa carte et sa place dans `monde.world`. La pénombre du sous-bois se règle au mètre du monde (`gloom` de `src/content/world.json`), jamais par zone. Une parcelle réservée = un rectangle `Parcel` (destination : `src/content/parcels.json`) ; un bâtiment posé = un rectangle `Plan` (un plan de `src/content/plans/`), dont les pièces entrent dans `builds` à la première visite (`seedPlans`) : jamais de bâtiment dessiné dans une carte. Test : `npm run test:monde` ; aperçu `.art-preview/monde.png` (`npm run art:monde`).
- Adresses : `?reset` efface la sauvegarde ; `?dieu` ouvre le panneau d'outils de test (`src/dieu/panel.ts`, HTML hors du canevas, absent sans `?dieu`). Un outil de test = une variante de `DieuCommand` (`src/events.ts`), un bouton du panneau, un cas de `WorldScene.dieu`, et il passe par les fonctions de GameState comme le jeu (jamais d'accès direct à la scène depuis le panneau).
- L'âge du bois (CONCEPTION « L'âge du bois ») : une seule matière bois, trois âges (neuf, patiné, vieux), une rampe par âge sur les mêmes signes (`woodAges` de `art/palette.ts`) ; tout bois travaillé se dessine avec ces signes, jamais une teinte propre à une pièce (la forme et la texture distinguent les pièces) ; le build tire `<image>-worn` et `<image>-old` (`art/lib/ages.ts`, `agedPalette` de `art/world/wood.ts`). Nouvel objet de bois : `"aged": true` dans props.json ou items.json (sinon `RAW_WOOD` de validate.ts, avec sa raison) ; validate.ts vérifie ses trois âges. L'âge d'une pièce de bois : `age` de ses réglages ; d'un objet posé en mode construction : `age` de la pièce posée (`withAge`, `ageOf` de `world/build.ts`, `agedKey` de `woodShape.ts`) ; un plan du bac à sable peut fixer `age` pour toutes ses pièces. Le rondin écorcé est un état (`peeled`), pas une clé. Aperçus : `.art-preview/bois-ages.png` (tout), `.art-preview/bois-ages-court.png` (à montrer : trois colonnes, x6, la cabane dans chaque âge ; produit par `npm run test:cabane`).
- Le bois : **un nouveau bois = un diamètre ou un état dans le contenu (`src/content/wood.json` : `sizes`, `looks`), pas une nouvelle clé.** Tout le bois du monde est la pièce de bois `wood-piece`, décrite par ses réglages (`WoodPieceSchema` : `size`, `length`, `shape`, `hewn`, `axis`, `notch`, `wedge`), gardés par GameState (`wood` d'un objet né ou changé, de ce qu'on tient ; `setWood`) et donnés dans Tiled en propriétés. Sa définition (dimensions, collision, prise, roulement, pivot, tas) : `src/world/woodPiece.ts` ; sa masse : `woodMass` (`mass.ts`) ; son image : les opérations de `src/world/woodShape.ts`, suivies à l'identique par le dessin (`art/world/wood-pieces.ts`, `composeWood`) et le jeu (`src/world/woodTexture.ts`) ; couper (grille de `grid` cm depuis le bout le plus proche, pas de pièce de moins de `min`), équarrir, fendre : `src/systems/wood.ts`. **Pièces fendues** (CONCEPTION, « Les pièces fendues ») : chaque aspect a sa section dans wood.json (`section` : forme, écorce, cœur, face d'appui, faces dressées) ; ses vues couchées se calculent (`art/world/wood-section.ts`), jamais dessinées à la main ; le pixel-artist ne règle que les matières (`art/world/wood-skin.ts`). La demi-bille repose écorce en bas, face en l'air ; le quartier écorce en bas, pointe en l'air (R ne change que son sens, `turnedWood`). Fendre : 3 coups par mètre commencé (`splitHits`), un seul coin ; les morceaux s'écartent si leur place est prise (`SPLIT`). Aperçus : `.art-preview/bois.png`, `.art-preview/bois-sections.png` ; test : `npm run test:sections` (recouvrement, positions après la coupe, règle D).
- Pierre : `"mass": "stone"` dans `props.json` (volume de la boîte de `dims` × `STONE_DENSITY`, `src/content/mass.ts`), comme `"wood"` pour le bois. Pierre naturelle : `"mass": {"matter": "stone", "fill": …}` (matters.json). **La roche est un réglage de la pierre** (`src/content/rocks.json` : nom, couleur, rampe de `art/palette.ts`, densité, dureté, prix ; la pierre commune est le calcaire, 2 400 kg/m³) : une nouvelle couleur de pierre = une nouvelle roche (`rock` de la matière `stone`, ou `"rock"` dans la masse d'une pierre), jamais une nouvelle clé. La pierre, un objet à la fois (docs/CONCEPTION.md, « La pierre, un objet à la fois ») : pierre brute en trois tailles (`small-`, `rough-stone`, `big-`), dalle (`slab`, le dé de l'abri), moellons de 30, 40, 50 cm (`short-`, `rubble-stone`, `long-`), un tas par taille et par longueur ; essais de dessin dans `art/proposals/` (hors jeu : `tools/essai-pierre.ts`, `tools/essai-murs.ts`). Tailler l'objet tenu dans l'autre main : `convert` (`from` : table de ce qu'on taille vers ce qu'il devient, `refuse`) d'un `harvest` à une main (la hachette sur le billot : la branche devient un piquet, le piquet une cheville).
- Matières (docs/CONCEPTION.md, « Les matières ») : le naturel est irrégulier (`natural` : 1 ou 2 formes, `<image>-b`, taille ± `vary` %, gardées par GameState, `world/natural.ts`), le travaillé régulier ; masse par la matière (`"mass": {"matter", "fill"}`, densités de `src/content/matters.json`, jamais en dur) ; chaque objet dit son métier (`trade`). Une transformation = une entrée de `src/content/transforms.json` (entrées, sorties, déchet, outils, poste, métier, geste réel ou `"soon"`), pas de code : la sortie pèse moins que l'entrée (validate.ts) ; en attendant son geste, ?dieu « Transformer » l'applique (`systems/transform.ts`). Aperçu : `.art-preview/briques.png` ; test : `npm run test:briques`.
- Le combat (CONCEPTION « Le combat ») : le corps et l'arme sont séparés. Une arme = `weapon` dans items.json (`length`, `grip`, `balance`, `efficiency`, `family`, `image` ; son tableau dans sa fiche) et **un seul dessin** couché vers l'est, tiré en huit angles par `art/lib/weapon.ts` (planche `weapon-<clé>`, pixel-artist) ; le geste du corps (gestures.json) choisit l'angle à chaque image (`weaponFrame`, ToolUse). Une attaque, une famille d'armes, ses postures (`when`, `chain`) : `src/content/combat.json`, jamais en dur ; une nouvelle posture (deux mains, bouclier, deux armes) ou attaque = une entrée, pas de code. **La zone de coup se calcule au sol, dans le monde, jamais d'après le dessin** (`sweeps` de combat.json : angle, portée, hauteur par image, images actives ; à l'écran la hauteur se mêle à la profondeur) ; à vérifier sur `.art-preview/carte-touche.png` (`npm run art:touche`). Portée, durées, dégâts, prix, zone : `src/world/strike.ts` (sans Phaser), prix dans stamina.json (`attackBase`, `attackPerKg`) ; le jeu : `src/systems/combat.ts`. Une cible = `target` dans props.json (`hp` : `infinite` tant que la partie ne garde pas les blessures, `matter` : planche `fx-<matter>`, `tilt`). Espace avec une arme qui sert (main active, ou l'autre si l'active est vide) attaque, toujours, même dans le vide ; toute autre touche : `docs/COMMANDES.md` (à tenir à jour). Test : `npm run test:combat` ; aperçu `.art-preview/combat.png`.
- **Ce qui se déclenche en passant se teste au franchissement depuis l'image d'avant, jamais à la position de l'instant** : `crossed` de `src/world/crossing.ts`, avec `Player.from` (les pieds à l'image d'avant). Un jeu qui rame fait plusieurs pas de physique de taille normale par image : une zone étroite (une porte, une sortie, un futur déclencheur) serait sautée. Les sorties de Tiled (`systems/exits.ts`) et les portes des bâtiments (`systems/interiors.ts`) y passent ; test : `tools/test-crossing.ts` (dans `npm run test:fast`).
- Tests de scénario dans le vrai jeu : `tools/lib/playtest.ts` (Chromium sans écran ; tous : `npm run test:scenarios`, hors du build), `npm run test:fendage`, `npm run test:implantation`, `npm run test:equarrissage`, `npm run test:tas`, `npm run test:perspective`, `npm run test:poteaux`, `npm run test:briques`, `npm run test:monde`, `npm run test:combat`.
- Fin de chantier, dans cet ordre : **commiter** ; **`npm run build`**, attendu (quelques secondes : `npm run check`, les tests rapides `npm run test:fast`, TypeScript, le build web) ; donner à Grégoire **le récapitulatif du chantier et ce qu'il doit essayer en jeu** ; puis lancer **`npm run test:scenarios:bg` en arrière-plan, sans l'attendre** (la suite des scénarios en navigateur, en parallèle, sur une copie figée du commit : le worktree `../rpg-game-tests`, rapport dans `../rpg-game-tests/rapport-scenarios.txt`), pour que Grégoire puisse envoyer la demande suivante. Quand les tests se terminent : un récapitulatif de quelques lignes (tout passe, ou quels scénarios échouent, pourquoi, et la correction proposée). Une correction se fait après la tâche en cours, dans un commit à part, jamais mélangée à elle. Avant une fusion dans main, la suite doit être passée sur le dernier commit. Un scénario se lance encore seul et en premier plan (`npm run test:<nom>`) quand on travaille dessus ; `npm run test:scenarios` lance toute la suite en premier plan (`SCENARIOS_JOBS` scénarios à la fois, 4 par défaut ; un tableau à la fin, sans s'arrêter au premier échec). Un nouveau scénario : son script `test:<nom>` et son nom dans `SCENARIOS` de `tools/run-scenarios.ts`.
